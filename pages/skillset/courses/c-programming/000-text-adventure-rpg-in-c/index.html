Text Adventure RPG in C

Concepts

A step-by-step build of a text adventure RPG in C — every step introduces one more C feature, in the order you'll actually reach for it while writing the game.

Step 1 — Verify your toolchain (gcc & gdb)

Before writing a single line of the game, confirm the compiler and debugger you'll use for the rest of this course are installed and on your PATH.

gcc --version
gdb --version
lldb --version   # macOS: gdb usually isn't installed, lldb is

You should see a version banner for each, for example gcc (Ubuntu 13.2.0) 13.2.0 and GNU gdb (Ubuntu 12.1) 12.1. If gcc isn't found, install the standard build tools for your platform first — build-essential on Debian/Ubuntu, Xcode Command Line Tools on macOS, or MinGW/WSL on Windows — then re-run both commands. Neither of those bundles gdb itself, so if that one command is still missing, see the install steps below.

Installing gdb on Linux, or using lldb on macOS

Linux — gdb is a normal package, separate from the compiler toolchain:

sudo apt install gdb      # Debian / Ubuntu
sudo dnf install gdb      # Fedora
sudo pacman -S gdb        # Arch

macOS — check for lldb instead; Xcode Command Line Tools already ship it, so it's very likely already installed:

lldb --version

Use lldb in place of gdb for the rest of this course — it debugs the same binaries and its commands map closely onto gdb's (Step 4 covers both). Getting gdb itself running on macOS needs a Homebrew install plus a manual code-signing step to get past System Integrity Protection, so lldb is the path this course follows there.

We'll use gcc to compile every step, and gdb — or lldb on macOS — very soon, when we start hunting real bugs in Step 4.

Step 2 — Hello, World in C

Every C program starts the same way: an entry point named main. Create a file called main.c with the following contents.

#include <stdio.h>
#include <string.h>

// Returns the game's opening greeting.
const char *greet(void) {
    return "Hello, World!";
}

// Hand-rolled unit test for greet(). Compares the returned string against
// what we expect, instead of just printing it and eyeballing the result.
void test_greet(void) {
    const char *result = greet();
    if (strcmp(result, "Hello, World!") == 0) {
        printf("[pass] test_greet\n");
    } else {
        printf("[fail] test_greet: got \"%s\"\n", result);
    }
}

// Runs every test in this file. Every later step adds its own test_*()
// function here, so run_tests() grows alongside the game.
void run_tests(void) {
    test_greet();
}

int main(int argc, char *argv[]) {
    if (argc > 1 && strcmp(argv[1], "test") == 0) {
        run_tests();
        return 0;
    }
    printf("%s\n", greet());
    return 0;
}

Compile it with gcc and run the resulting binary:

gcc main.c -o hello
./hello

That prints the greeting. Run the tests instead by passing test as an argument:

./hello test
Line-by-line walkthrough

#include <stdio.h> pulls in the standard I/O library so printf is available, and #include <string.h> brings in strcmp for comparing strings. greet() returns a const char * — a pointer to text it doesn't own — rather than printing directly, which is what makes it testable: test_greet() can call it and compare the result against the exact string we expect, instead of just printing something and eyeballing it. main is where execution begins; argc and argv carry the arguments the program was launched with, so checking argv[1] against "test" is how ./hello test is told apart from a normal run. return 0; tells the operating system the program finished successfully.

The testing pattern for the rest of this course

From here on, every step keeps its game logic in small functions that return a value rather than print one, each with a matching test_<name>() that checks that value. Every test gets one line inside run_tests(), which lives outside main and is the single place all of this file's tests are collected — no external testing framework, all of it reachable through that same test argument.

Step 2.1 — Anatomy of greet(): char, pointer & void

const char *greet(void) packs three ideas into one line. Taken apart piece by piece:

char — C's character type

One char holds a single byte, typically one letter, digit or symbol. A piece of text like "Hello, World!" is stored in memory as a run of char values sitting next to each other, followed by a hidden zero byte ('\0') that marks where the text ends. That whole run is what C calls a "string" — there's no separate string type.

* — the pointer

The * makes it a pointer: a variable that holds a memory address instead of holding a value directly. char * reads as "a pointer to a char" — in practice, the address of the first character of one of those runs described above. Reading the rest of the string just means walking forward through memory, one char at a time, until the zero byte is reached. That's why greet() can return the whole greeting as a single pointer instead of copying every character.

const — the read-only promise

The leading const is a promise about that pointer: whoever receives it agrees not to modify the characters it points to. It documents that greet() hands out a read-only view of its text, which matters here because the string literal "Hello, World!" lives in memory the program isn't allowed to write to anyway.

void — two different meanings

void shows up twice in this file, meaning two different things depending on where it sits. Inside the parentheses — greet(void) — it means "takes no parameters." As a return type — void test_greet(void) — it means "returns nothing." greet uses the first sense but not the second, since it does return something: that const char *.

Step 2.2 — Anatomy of test_greet()

test_greet() follows a shape every later test in this course repeats: call the function, compare what it returned against what's expected, and report pass or fail. Taken apart piece by piece:

const char *result = greet(); — calling greet() and keeping its answer

This calls greet() and stores what it returns — the pointer described in Step 2.1 — in a local variable named result. Nothing is printed yet; the point of a test is to check a value before anything is shown, rather than printing first and trusting your eyes to catch a mistake.

strcmp(result, "Hello, World!") == 0 — comparing string content, not pointers

You can't compare two C strings with == — that would compare the two pointers' addresses, not the characters they point to, and would almost always be false even for identical-looking text. strcmp walks both strings character by character instead, and returns 0 when every character matches (a nonzero result, positive or negative, means they differ). Comparing that return value against 0 is how C spells "these two strings are equal."

if / else and %s — reporting pass or fail

The if branch runs when the comparison matched, printing a fixed "[pass] test_greet" line — there's nothing more to say when the result was exactly right. The else branch runs when it didn't, and uses %s inside printf to splice the actual result string into the message, so a failure reads [fail] test_greet: got "whatever greet() actually returned" instead of just "it failed" — enough detail to debug without reaching for gdb or lldb.

Step 2.3 — Anatomy of the main function

main is the one function every C program must have — it's where the operating system hands control to your code — and this file's main does two different things depending on how it was launched. Taken apart piece by piece:

int argc, char *argv[] — the arguments the program was started with

argc ("argument count") is how many command-line arguments were passed, always counting the program's own name as the first one. argv ("argument vector") is an array of C strings holding those arguments — argv[0] is the program name (./hello), and argv[1], if it exists, is the first thing typed after it. Running ./hello test means argc is 2 and argv[1] is the string "test".

argc > 1 && strcmp(argv[1], "test") == 0 — why the order of these two checks matters

If no extra argument was given, argv[1] doesn't exist, and reading it would be a bug. C's && is short-circuiting: if argc > 1 is false, the right-hand side is never evaluated at all, so strcmp(argv[1], ...) only runs once it's already known that argv[1] is safe to read. Swapping the order of the two checks would remove that guarantee.

return 0; — telling the operating system it worked

A C program's exit code is how it reports success or failure to whatever launched it — a shell, a script, a CI pipeline. return 0; from main is the universal convention for "no error," and it's what a shell checks when you run echo $? right after the program exits. Both branches of this main — the test path and the normal path — return 0, since neither one has anything that can fail yet.

Step 3 — Multi-file, Variables, types & printf formatting

So far the whole game has lived in one file. Before it grows any further, split it for the first time: move greet() and test_greet() out of main.c and into their own module, greeting.h and greeting.c. Along the way, main.c picks up a small intro banner that introduces a few C types and how printf formats each one.

Create greeting.h — a header, declaring what the module offers without defining any of it:

#ifndef GREETING_H
#define GREETING_H

// Returns the game's opening greeting.
const char *greet(void);

// Hand-rolled unit test for greet().
void test_greet(void);

#endif

Create greeting.c — the definitions the header promised, moved here unchanged from Step 2:

#include <stdio.h>
#include <string.h>
#include "greeting.h"

const char *greet(void) {
    return "Hello, World!";
}

void test_greet(void) {
    const char *result = greet();
    if (strcmp(result, "Hello, World!") == 0) {
        printf("[pass] test_greet\n");
    } else {
        printf("[fail] test_greet: got \"%s\"\n", result);
    }
}

Update main.c to include the new header instead of defining greet() itself, and add print_intro() — the new banner, built from an int, a float and a char:

#include <stdio.h>
#include <string.h>
#include "greeting.h"

// Prints the game's opening banner: the greeting plus a few values of
// different C types, each shown with a matching printf format specifier.
void print_intro(void) {
    int version = 1;
    float starting_gold = 10.5f;
    char class_initial = 'W';

    printf("%s\n", greet());
    printf("Text Adventure RPG -- version %d\n", version);
    printf("You start with %.1f gold as a %c-class hero.\n", starting_gold, class_initial);
}

// Runs every test in this file (and the modules it includes).
void run_tests(void) {
    test_greet();
}

int main(int argc, char *argv[]) {
    if (argc > 1 && strcmp(argv[1], "test") == 0) {
        run_tests();
        return 0;
    }
    print_intro();
    return 0;
}

Every .c file that got compiled separately before now has to be listed on the same command line, so gcc can compile and link all of them into one binary:

gcc main.c greeting.c -o hello
./hello
./hello test
Why split into files, and what a .h file is for

A .c file is where code is defined — the actual body of a function. A .h file is where code is declared — just the name, parameters and return type, a promise of what exists without saying how it works. main.c can now call greet() and test_greet() just by including greeting.h, without needing to see — or recompile — greeting.c itself. As the game grows, each new area (rooms, inventory, combat) gets its own .h/.c pair instead of one file growing without end.

#ifndef / #define / #endif — the include guard

If two different .c files both #include "greeting.h" — which main.c and greeting.c now both do — the compiler would see the declarations inside it twice and reject the file as a redefinition. The three lines wrapping the header are an include guard: the first time greeting.h is included, GREETING_H isn't defined yet, so its contents run and #define GREETING_H marks it as seen; any later #include of the same header finds GREETING_H already defined and skips straight to #endif, contents untouched. Every header this course writes from here on starts and ends the same way.

int, float & char — three more C types

int holds a whole number — no fractional part — and is the natural type for a version number or a room count. float holds a number with a fractional part, stored as an approximation rather than an exact value, which is normal for something like a gold amount that doesn't need bank-level precision. char, met already in Step 2.1 as half of a string, is just as often a single standalone character on its own, like class_initial here — C makes no distinction between "a character" and "a string of length one holding that character."

%d, %.1f, %c — matching a format specifier to a type

Each % placeholder in a printf format string consumes one of the arguments after it, in order, and has to match that argument's type or the output is garbage. %d prints an int. %c prints a single char. %f prints a float or double; the .1 in %.1f is a precision — "round to one digit after the decimal point" — which is why 10.5f prints as 10.5 rather than the longer decimal a float can actually hold internally. This is the same %s from Step 2 doing the same job for greet()'s const char *, just alongside two new specifiers for two new types.

print_intro() doesn't get a test_<name>() of its own yet — it only prints, and there's nothing meaningful to strcmp or compare until later steps give it real game state to build the banner from. For now, run ./hello without test and check the banner by eye; the testing pattern from Step 2 picks back up as soon as a function returns something worth asserting on.

Step 4 — Debugging with gdb/lldb

A debugger lets you pause a running program, look at its variables, and step through it one line at a time — instead of guessing from printf output. We'll use test_greet(), now living in greeting.c since Step 3's split, as the example: set a breakpoint on it, run ./hello test under the debugger, and watch result get filled in by greet().

Either debugger needs the binary built with debug symbols — the -g flag keeps the source line and variable information gdb/lldb read. With the project now split across files, every .c file goes on the same compile line, same as the plain build in Step 3:

gcc -g main.c greeting.c -o hello

Pick whichever debugger Step 1 found on your system.

Debugging with gdb (Linux) 
gdb ./hello
(gdb) break test_greet
(gdb) run test
(gdb) next
(gdb) next
(gdb) print result
(gdb) continue
(gdb) quit

break test_greet sets a breakpoint at the start of that function. run test launches ./hello with test as its argument — the same argv[1] check from Step 2 — and execution stops the moment it enters test_greet. Each next runs one source line without stepping into the functions it calls, so two of them land right after const char *result = greet(); has executed. At that point print result shows the pointer greet() returned along with the string it points to — something like $1 = 0x... "Hello, World!" — confirming the value test_greet's strcmp check is about to compare. continue lets the program run to completion, and quit exits gdb.

Debugging with lldb (macOS) 
lldb ./hello
(lldb) breakpoint set --name test_greet
(lldb) run test
(lldb) next
(lldb) next
(lldb) print result
(lldb) continue
(lldb) quit

The commands mirror gdb's almost exactly. breakpoint set --name test_greet stops execution at that function (b test_greet also works, as a shorthand). run test launches ./hello test, and lldb halts as soon as it reaches test_greet. Two next commands step over const char *result = greet(); the same way, and print result reports both the pointer and the string it points to — (const char *) 0x... "Hello, World!". continue resumes the program to the end, and quit exits lldb.

In both sessions the payoff is the same: instead of trusting that greet() returned the right thing, you watched result hold the exact pointer and string it produced, right before test_greet's own strcmp check made that same comparison. That's the whole point of a debugger — for a one-line function like greet() the test alone is enough, but as the game grows this is how you'll pin down which line actually broke.

More debugging commands: step, finish, backtrace & more

The walkthroughs above cover enough to inspect one function. A few more commands come up constantly once the game has more than one function calling another:

# gdb
(gdb) step               # or s — step INTO the next line, entering any function call on it
(gdb) finish              # run until the current function returns, showing what it returned
(gdb) backtrace           # or bt — show the full chain of calls that got you here
(gdb) list                # or l — show source lines around where you're stopped
(gdb) info breakpoints    # list every breakpoint and how many times each has been hit
(gdb) delete 1            # remove breakpoint number 1

# lldb
(lldb) step               # or s — step INTO the next line, entering any function call on it
(lldb) finish              # run until the current function returns, showing what it returned
(lldb) bt                  # or thread backtrace — show the full chain of calls that got you here
(lldb) list                # or l — show source lines around where you're stopped
(lldb) breakpoint list     # list every breakpoint and how many times each has been hit
(lldb) breakpoint delete 1 # remove breakpoint number 1

step is next's opposite: instead of running over a function call, it follows execution into it — which is how the earlier walkthrough's two nexts could have been a step into greet() instead, landing on its return line. Be careful pointing step at a call the debugger has no source for, like strcmp(): it'll still step in, just into raw disassembly with no code to read, and you'll want finish to get back out.

finish runs the rest of the current function and stops the instant it returns — useful once you've stepped somewhere you didn't mean to, or once you've seen enough of a function's internals and just want its answer. For a function like greet() it prints that answer directly: something like Return value: (const char *) $0 = 0x... "Hello, World!", the same pointer-and-string pairing print result showed earlier, just captured the moment it's handed back to the caller.

backtrace lists every function call that's currently on the stack, innermost first — with a breakpoint on test_greet, that's already three deep: test_greet, called by run_tests, called by main. It's the fastest way to answer "how did execution even get here" once functions start calling functions several layers deep.

list reprints the source around the current line without needing to step anywhere — handy after a backtrace jumps your attention to a frame you weren't just looking at.

Once more than one breakpoint is set, info breakpoints (gdb) / breakpoint list (lldb) shows all of them together with a hit count, and delete <N> (gdb) / breakpoint delete <N> (lldb) removes the one you no longer need — both take the number shown when the breakpoint was first set, like the Breakpoint 1 from break test_greet earlier in this step.

Debugging across multiple files

Now that greet() and test_greet() live in greeting.c instead of main.c, breakpoints work exactly the same way — a function name alone is still enough as long as it's unique across every file compiled with -g, which is why break test_greet above didn't need to change at all. When a name isn't enough — a specific line rather than a whole function, or a static helper that exists in two files — name the file too. Here's a breakpoint on greeting.c line 6, the return "Hello, World!"; inside greet() itself, rather than on test_greet which calls it:

# gdb
(gdb) break greeting.c:6
(gdb) run test

# lldb
(lldb) breakpoint set --file greeting.c --line 6
(lldb) b greeting.c:6   # shorthand, works the same as gdb's
(lldb) run test

Execution now stops one function earlier than before — inside greet(), not test_greet() — which is the whole point of naming a line: result isn't in scope yet at this breakpoint, since it belongs to test_greet's stack frame, not greet's. Stepping behaves the same across file boundaries as it does within one: step (or s) follows execution into a function's definition no matter which file it lives in, while next runs over the call without entering it, regardless of file — so stepping out of greet() here with a couple of steps lands you right back in test_greet, in greeting.c the whole time. To see every source file the debugger currently knows about — useful for confirming a file actually got compiled with debug info — gdb has info sources and lldb has target modules dump sources.

Step 5 — Makefile

Typing the full gcc command by hand gets old fast. Create a file named exactly Makefile next to main.c:

CC = gcc
SRCS = main.c greeting.c
BIN = hello

all: $(BIN)

$(BIN): $(SRCS)
	$(CC) $(SRCS) -o $(BIN)

debug: $(SRCS)
	$(CC) -g $(SRCS) -o $(BIN)

test: $(BIN)
	./$(BIN) test

clean:
	rm -rf $(BIN) $(BIN).dSYM

.PHONY: all debug test clean

Now the whole project builds, tests and rebuilds for debugging with short, memorable commands:

make          # build ./hello
make test     # build, then run ./hello test
make debug    # build with -g, for gdb/lldb (Step 4)
make clean    # remove ./hello and its debug symbols
Reading a Makefile: targets, prerequisites, recipes

Each block is target: prerequisites followed by an indented (tab, not spaces) recipe — the shell command that builds it. make only re-runs a recipe when its prerequisites are newer than the target, so an unchanged project rebuilds nothing. CC, SRCS and BIN are just variables, expanded with $(...), so the file list and binary name are only written once. .PHONY marks targets that aren't real files — without it, a stray file named test or clean would stop those targets from running.
