Text Adventure RPG in Java

OOP

The same text adventure RPG as the C course, built the traditional Java way: plain javac/java, a real JVM, ordinary classes and objects, and jdb — the JDK's own command-line debugger — instead of an IDE.

Step 1 — Verify your toolchain (javac, java & jdb)

Every step compiles with javac and runs with java, and Step 5 debugs with jdb — all three ship together in any standard JDK, so there's nothing extra to install beyond the JDK itself.

javac -version
java -version
jdb -version

Each should print a version banner, for example javac 25.0.1, openjdk version "25.0.1" ..., and This is jdb version 25.0 (Java SE version 25.0.1). If none of them are found, install a JDK — SDKMAN (sdk install java) is the easiest cross-platform path; Linux package managers and the Windows/macOS installers from your JDK vendor of choice work too.

jdb isn't a separate tool

Unlike the C course's gdb/lldb, which are independent projects installed on their own, jdb is part of the JDK distribution itself — the same download that gives you javac and java gives you jdb too, in the same bin/ directory. If javac -version and java -version both work, jdb -version almost certainly will too.

Step 2 — Hello World, compiled and run with javac/java

Every step in this course lives in one file, HelloWorld.java, the same way the C course grew main.c. Start with the same greet / test / dispatch shape:

public class HelloWorld {
    static String greet() {
        return "Hello, World!";
    }

    static void testGreet() {
        String result = greet();
        if (result.equals("Hello, World!")) {
            System.out.println("[pass] testGreet");
        } else {
            System.out.println("[fail] testGreet: got \"" + result + "\"");
        }
    }

    static void runTests() {
        testGreet();
    }

    public static void main(String[] args) {
        if (args.length > 0 && args[0].equals("test")) {
            runTests();
            return;
        }
        System.out.println(greet());
    }
}

Compile with javac, then run the class file it produces with java — no separate link step, no output binary to name:

javac HelloWorld.java
java HelloWorld
java HelloWorld test
Why there's no "./hello" here

javac compiles HelloWorld.java into HelloWorld.class — JVM bytecode, not machine code — and java HelloWorld starts a JVM that loads and runs that bytecode. There's nothing to chmod +x or execute directly; java is always the thing actually running, with your class loaded inside it.

Step 3 — Classes & objects: Player as a real Java class

Add a second, non-public class to the same file — Java allows more than one top-level class per file, as long as only one is public and it matches the filename. Player starts as plain as a class gets: two fields, no behavior of its own yet:

// A plain Java class: two fields, no behavior of its own yet.
class Player {
    int health;
    int gold;
}

Add a demo() that creates one and works with its fields directly, and call it from main():

static void demo() {
    Player player = new Player();
    player.health = 100;
    player.gold = 0;
    player.gold = player.gold + 10;
    System.out.println("Health: " + player.health + ", Gold: " + player.gold);
}
javac HelloWorld.java
java HelloWorld
new Player() — an object on the heap, not a struct in a byte count

new Player() allocates space for a Player on the regular JVM heap and hands back a reference to it — there's no malloc, no size to compute, no matching free. The garbage collector reclaims it automatically once nothing references it anymore. player.health and player.gold read and write the object's fields directly, the same way player->health would in C, just without a ->.

demo() doesn't get a test<Name>() of its own yet, for the same reason the earlier courses' first memory/struct demos didn't — it only prints, with nothing to assert on until later steps give it real game state. runTests() still just checks testGreet().

Step 4 — Fields, constructors & the this keyword

Setting each field by hand after new Player() is easy to forget or get wrong. Give Player a constructor instead, so a Player can never exist half-initialized:

class Player {
    int health;
    int gold;

    Player(int health, int gold) {
        this.health = health;
        this.gold = gold;
    }
}

demo() gets shorter — one call instead of three separate assignments:

static void demo() {
    Player player = new Player(100, 0);
    player.gold = player.gold + 10;
    System.out.println("Health: " + player.health + ", Gold: " + player.gold);
}
javac HelloWorld.java
java HelloWorld
this.health vs health — why both names are needed

The constructor's parameter is also named health, so inside the constructor's body, plain health refers to the parameter — it shadows the field of the same name. this refers to the object currently being constructed, so this.health reaches past the shadowing parameter to the field itself. this.health = health; reads as "this object's health field gets the value of the health parameter" — two different things that happen to share a name.

Step 5 — Debugging with jdb

Compile with -g so jdb has full source line and local-variable info to work with — without it, print/locals on a local variable can come back empty:

javac -g HelloWorld.java

Launch jdb the same way you'd run the program — the class name, then its arguments — and set a breakpoint on testGreet() from Step 2, the same target the other courses' debugging steps used:

jdb HelloWorld test

[pass] testGreet

stop in vs gdb's break

jdb's breakpoint command is stop in ClassName.methodName — no line number needed, and no separate compile flag beyond -g. The "Deferring breakpoint" message just means the HelloWorld class hadn't been loaded into the JVM yet when the breakpoint was requested; jdb resolves it automatically the moment the class does load, right as run starts the program.

next, print, where & cont — the same shape as gdb/lldb

next steps over a line the same way it does in gdb/lldb. print <expr> shows a value — result reads "Hello, World!" right where the C course's gdb/lldb sessions found the equivalent pointer. where is jdb's name for a backtrace, showing the exact same three-deep call chain — testGreet called by runTests called by main — that the other courses' debugging steps walked. cont resumes to the next breakpoint or the program's end, same as continue.
