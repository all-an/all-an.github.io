Text Adventure RPG in Java

OOP

A text adventure RPG built the traditional Java way: plain javac/java, a real JVM, ordinary classes and objects, and jdb — the JDK's own command-line debugger — instead of an IDE.

Step 1 — Verify your toolchain (javac, java & jdb)

Every step compiles with javac and runs with java, and Step 5 debugs with jdb — all three ship together in any standard JDK, so there's nothing extra to install beyond the JDK itself.

javac -version
java -version
jdb -version

Each should print a version banner, for example javac 25.0.1, openjdk version "25.0.1" ..., and This is jdb version 25.0 (Java SE version 25.0.1). If none of them are found, install a JDK — SDKMAN (sdk install java) is the easiest cross-platform path; Linux package managers and the Windows/macOS installers from your JDK vendor of choice work too.

jdb isn't a separate tool

Unlike gdb/lldb, which are independent projects installed on their own, jdb is part of the JDK distribution itself — the same download that gives you javac and java gives you jdb too, in the same bin/ directory. If javac -version and java -version both work, jdb -version almost certainly will too.

Step 2 — Hello World, compiled and run with javac/java

Every step in this course lives in one file, HelloWorld.java. Start with a greet / test / dispatch shape:

public class HelloWorld {
    static String greet() {
        return "Hello, World!";
    }

    static void testGreet() {
        String result = greet();
        if (result.equals("Hello, World!")) {
            System.out.println("[pass] testGreet");
        } else {
            System.out.println("[fail] testGreet: got \"" + result + "\"");
        }
    }

    static void runTests() {
        testGreet();
    }

    public static void main(String[] args) {
        if (args.length > 0 && args[0].equals("test")) {
            runTests();
            return;
        }
        System.out.println(greet());
    }
}

Compile with javac, then run the class file it produces with java — no separate link step, no output binary to name:

javac HelloWorld.java
java HelloWorld
java HelloWorld test
Why there's no "./hello" here

javac compiles HelloWorld.java into HelloWorld.class — JVM bytecode, not machine code — and java HelloWorld starts a JVM that loads and runs that bytecode. There's nothing to chmod +x or execute directly; java is always the thing actually running, with your class loaded inside it.

Step 3 — Classes & objects: Player as a real Java class

Add a second, non-public class to the same file — Java allows more than one top-level class per file, as long as only one is public and it matches the filename. Player starts as plain as a class gets: two fields, no behavior of its own yet:

// A plain Java class: two fields, no behavior of its own yet.
class Player {
    int health;
    int gold;
}

Add a demo() that creates one and works with its fields directly, and call it from main():

static void demo() {
    Player player = new Player();
    player.health = 100;
    player.gold = 0;
    player.gold = player.gold + 10;
    System.out.println("Health: " + player.health + ", Gold: " + player.gold);
}
javac HelloWorld.java
java HelloWorld
new Player() — an object on the heap

new Player() allocates space for a Player on the regular JVM heap and hands back a reference to it — no size to compute and nothing to release by hand. The garbage collector reclaims it automatically once nothing references it anymore. player.health and player.gold read and write the object's fields directly.

demo() doesn't get a test<Name>() of its own yet — it only prints, with nothing to assert on until later steps give it real game state. runTests() still just checks testGreet().

Step 4 — Fields, constructors & the this keyword

Setting each field by hand after new Player() is easy to forget or get wrong. Give Player a constructor instead, so a Player can never exist half-initialized:

class Player {
    int health;
    int gold;

    Player(int health, int gold) {
        this.health = health;
        this.gold = gold;
    }
}

demo() gets shorter — one call instead of three separate assignments:

static void demo() {
    Player player = new Player(100, 0);
    player.gold = player.gold + 10;
    System.out.println("Health: " + player.health + ", Gold: " + player.gold);
}
javac HelloWorld.java
java HelloWorld
this.health vs health — why both names are needed

The constructor's parameter is also named health, so inside the constructor's body, plain health refers to the parameter — it shadows the field of the same name. this refers to the object currently being constructed, so this.health reaches past the shadowing parameter to the field itself. this.health = health; reads as "this object's health field gets the value of the health parameter" — two different things that happen to share a name.

Step 6 — Reading player input with Scanner

The game needs to hear from the player. java.util.Scanner is the standard library's line reader — wrap it around a source of text and call nextLine() to pull one line at a time. Add the import at the very top of the file, above public class HelloWorld:

import java.util.Scanner;

Add an askName() that prompts, reads a line, and builds a welcome message — taking the Scanner as a parameter rather than creating its own, so a test can hand it one backed by a fixed string:

// Prompts for the player's name, reads one line, and returns a welcome
// message. A blank line falls back to "stranger" so the message is never
// left dangling. The Scanner is passed in so tests can supply their own.
static String askName(Scanner in) {
    System.out.print("What is your name, adventurer? ");
    String name = in.nextLine().trim();
    if (name.isEmpty()) {
        name = "stranger";
    }
    return "Welcome, " + name + "!";
}

Because askName() takes its Scanner as an argument, its test can build one from a plain string literal — no keyboard involved:

static void testAskName() {
    Scanner in = new Scanner("Aria\n");
    String result = askName(in);
    if (result.equals("Welcome, Aria!")) {
        System.out.println("[pass] testAskName");
    } else {
        System.out.println("[fail] testAskName: got \"" + result + "\"");
    }
}

Register it in runTests(), and wire a real Scanner on System.in into main()'s non-test path, closing it once at the end:

static void runTests() {
    testGreet();
    testAskName();
}

public static void main(String[] args) {
    if (args.length > 0 && args[0].equals("test")) {
        runTests();
        return;
    }
    System.out.println(greet());
    Scanner in = new Scanner(System.in);
    System.out.println(askName(in));
    demo();
    in.close();
}

A Scanner wraps a source — the keyboard is just one option

new Scanner(System.in) reads from standard input, the keyboard. new Scanner("Aria\n") reads from that string as if it had been typed. Same class, same nextLine(), different source — which is exactly why askName() takes the Scanner as a parameter instead of building its own: the test path feeds it a known string and asserts on the result, while main() feeds it the real keyboard.

nextLine() vs next() vs nextInt()

nextLine() reads everything up to and including the next newline, and hands back the text without that newline — so "go north" comes through as one String. next() reads a single whitespace-delimited token — just "go" — and stops. nextInt() parses a number but leaves the newline sitting in the buffer, which is the classic reason a later nextLine() mysteriously returns an empty string. This course sticks to nextLine() everywhere and does its own splitting later, in Step 10.

Why the Scanner gets closed — and only once

A Scanner holds its underlying source open; close() releases it. Closing a Scanner that wraps System.in also closes System.in itself for the rest of the JVM's life, so there can only ever be one, closed once, at the very end of main() — never inside a helper that runs mid-game. Later steps move this into a try-with-resources block (Step 13) so the close happens automatically even when something throws.

Step 7 — Conditionals & the game loop

One line of input isn't a game. A text adventure keeps asking for a command, reacting to it, and asking again — until the player quits or the story ends. Two pieces make that work: a function that turns one command into a response, and a loop that keeps calling it.

Start with the response function — an if / else if / else chain, one branch per command, with the else catching anything unrecognized:

// Turns one already-normalized command into the text shown to the player.
// Anything unrecognized falls through to a gentle nudge rather than silence.
static String respondTo(String command) {
    if (command.equals("look")) {
        return "You stand at the mouth of a dark cave. A path leads north.";
    } else if (command.equals("north")) {
        return "You walk north into the gloom.";
    } else if (command.equals("help")) {
        return "Commands: look, north, help, quit";
    } else {
        return "You can't do that here.";
    }
}
static void testRespondTo() {
    boolean ok = respondTo("look").startsWith("You stand at the mouth")
            && respondTo("help").contains("quit")
            && respondTo("mumble").equals("You can't do that here.");
    System.out.println(ok ? "[pass] testRespondTo" : "[fail] testRespondTo");
}

Now the loop. It has two separate reasons to stop — the player types quit, or input runs out entirely — so it's written as while (true) with a break for each:

// Reads commands until the player types "quit" or input ends. Each command
// is trimmed and lowercased so " Look " and "look" mean the same thing.
static void playLoop(Scanner in) {
    while (true) {
        System.out.print("> ");
        if (!in.hasNextLine()) {
            break;
        }
        String command = in.nextLine().trim().toLowerCase();
        if (command.equals("quit")) {
            System.out.println("Farewell, adventurer.");
            break;
        }
        System.out.println(respondTo(command));
    }
}

Add testRespondTo() to runTests(), and call playLoop(in) from main() in place of the old single askName() print — after the welcome, before the Scanner is closed:

System.out.println(greet());
Scanner in = new Scanner(System.in);
System.out.println(askName(in));
playLoop(in);
in.close();

java HelloWorld
java HelloWorld test
if / else if / else — first match wins

Java tests each condition from the top down and runs the body of the first one that's true, skipping every branch below it. The trailing else has no condition — it runs only when every test above failed, which is where unknown commands land. Because each branch here ends in return, control leaves respondTo() immediately; there's no fall-through between branches the way there is in a bare C-style switch. Step 11 swaps this chain for an enum-driven switch once the command set is fixed.

while (true) + break, instead of a loop condition

A while (condition) loop fits when there's one clean test to repeat on. This loop stops for two unrelated reasons — a quit command and end-of-input — that don't compress into a single boolean without an awkward flag variable, so the idiom is while (true) with a break at each exit. in.hasNextLine() is the end-of-input guard: it returns false when the stream is exhausted (a piped-in file that ran out, or Ctrl-D at the keyboard), so the loop ends cleanly instead of nextLine() throwing NoSuchElementException.

trim().toLowerCase() — normalizing before comparing

String comparison with equals() is exact: "Look", "look" and " look " are three different values. Rather than list every casing in respondTo(), the loop normalizes once — trim() drops leading and trailing whitespace, toLowerCase() folds the case — so every branch downstream can compare against a single lowercase form. Each call returns a new String; the original input is untouched, because String is immutable (Step 4's constructor discussion, applied to a built-in type).

Step 8 — Methods: organizing game logic

Two fixed strings are already buried inside respondTo(): the cave description and the command list. Both are about to be needed in more than one place, so lift each into its own small, named method that does exactly one thing:

// The opening description of the starting room. Its own method so the text
// lives in one place — used by the "look" command and the game's intro.
static String caveDescription() {
    return "You stand at the mouth of a dark cave. A path leads north.";
}

// The list of commands the player can type. Shown by "help" and after any
// command the game doesn't recognize.
static String helpText() {
    return "Commands: look, north, help, quit";
}

respondTo() now reads as a table of intent — each branch names what happens, with the how delegated:

static String respondTo(String command) {
    if (command.equals("look")) {
        return caveDescription();
    } else if (command.equals("north")) {
        return "You walk north into the gloom.";
    } else if (command.equals("help")) {
        return helpText();
    } else {
        return "You can't do that here. Type 'help' for options.";
    }
}

Do the same to main(). Everything that makes up one play session — greet, ask the name, show the room, loop — moves into a startGame() method, leaving main() responsible only for the test switch and the Scanner's lifetime:

// Runs one full play session against the given input source.
static void startGame(Scanner in) {
    System.out.println(greet());
    System.out.println(askName(in));
    System.out.println(caveDescription());
    playLoop(in);
}

public static void main(String[] args) {
    if (args.length > 0 && args[0].equals("test")) {
        runTests();
        return;
    }
    Scanner in = new Scanner(System.in);
    startGame(in);
    in.close();
}

The demo() method from Steps 3–4 was scaffolding to hold a Player while the game had nowhere to put one. The game now has real methods to grow into, so delete demo() — the Player class stays and gets wired in properly in Step 9. runTests() is unchanged: testGreet(), testAskName(), testRespondTo().

One method, one job — and one reason to change

caveDescription() returns a description; helpText() returns the command list; playLoop() runs the loop; startGame() sequences a session. Each has a single responsibility, so each has a single reason to be edited later — changing the room's wording touches caveDescription() and nothing else. A method whose name needs an "and" to describe it ("greets the player and reads commands and…") is usually two methods wearing one signature.

Passing the Scanner down instead of reaching for a global

startGame() and playLoop() both need the input source, so it's handed to them as a parameter, threaded down from the one place it's created in main(). Java has no true global variables — the closest thing is a static field on the class — and a static Scanner shared implicitly by every method is exactly what makes code hard to test. An explicit parameter keeps respondTo() and its helpers provably independent of where input comes from.

void vs a return type — what a method hands back

caveDescription() is declared String because its whole purpose is to produce a value for the caller to use. startGame() and playLoop() are declared void: they exist for their side effect — printing to the screen, consuming input — and have nothing meaningful to return. A rough rule that holds through the rest of this course: methods that compute return a value and get a test<Name>(); methods that only drive the console are void and are checked by playing the game.

Step 9 — Arrays & ArrayList: rooms and inventory

The game needs two lists with opposite shapes. The set of rooms is decided up front and never changes size — a plain array. The player's pack starts empty and grows every time they pick something up — an ArrayList. Add the import at the top:

import java.util.ArrayList;

The rooms are a static final array literal — fixed length, shared by the whole class:

Player gains an inventory field, initialized in the constructor so every Player starts with an empty — never null — pack:

Array or ArrayList — let the size decide

An array's length is fixed the moment it's created: { "cave mouth", "tunnel", "underground lake" } is length 3 forever, and there's no add — you'd have to allocate a bigger array and copy. That's the right trade when the count is known and stable, like the room list. An ArrayList carries a little bookkeeping overhead in exchange for add(), remove() and automatic resizing — the right trade when the count isn't known up front, like an inventory. Reach for an array only when the size genuinely never changes; otherwise ArrayList is the default.

ArrayList<String>, new ArrayList<>(), and the empty-not-null rule

The <String> is a generic type argument — it tells the compiler this list holds Strings and nothing else, so inventory.add(42) won't compile and inventory.get(0) is known to be a String without a cast. On the right of =, new ArrayList<>() uses the empty diamond <>: the type is inferred from the field's declaration, so it isn't repeated. Initializing it in the constructor rather than leaving it to default means inventory is never null — takeItem() can call .add() on the very first turn without a NullPointerException.

.length vs .size(), and iterating either one

An array's element count is the field ROOMS.length — no parentheses. An ArrayList's is the method player.inventory.size() — with parentheses. Mixing them up is one of the most common early Java compile errors. Both work with the enhanced for loop, though: for (String room : ROOMS) and for (String item : player.inventory) read identically. String.join(", ", player.inventory) used above is a shortcut for that loop when all you want is the elements stitched together with a separator.

Step 10 — Strings: parsing player commands

So far every command is a single word. Real adventure input has two parts — a verb and a noun: go north, take rusty key, drop rope. Split the line on its first run of whitespace, keeping everything after it as one piece:

// Splits a command line into a verb and the rest as its noun.
// "take rusty key" -> { "take", "rusty key" };  "look" -> { "look", "" }.
static String[] parseCommand(String input) {
    String[] parts = input.trim().split("\\s+", 2);
    String verb = parts[0];
    String noun = parts.length > 1 ? parts[1] : "";
    return new String[] { verb, noun };
}
static void testParseCommand() {
    String[] a = parseCommand("take rusty key");
    String[] b = parseCommand("look");
    boolean ok = a[0].equals("take") && a[1].equals("rusty key")
            && b[0].equals("look") && b[1].isEmpty();
    System.out.println(ok ? "[pass] testParseCommand" : "[fail] testParseCommand");
}

respondTo() now branches on the verb and uses the noun, so one take branch handles any item and go handles any direction. Direction handling moves into its own helper to keep the chain flat:

static String respondTo(String command, Player player) {
    String[] parsed = parseCommand(command);
    String verb = parsed[0];
    String noun = parsed[1];

    if (verb.equals("look")) {
        return caveDescription();
    } else if (verb.equals("go")) {
        return respondToGo(noun);
    } else if (verb.equals("take")) {
        return noun.isEmpty() ? "Take what?" : takeItem(player, noun);
    } else if (verb.equals("inventory")) {
        return describeInventory(player);
    } else if (verb.equals("help")) {
        return helpText();
    } else {
        return "You can't do that here. Type 'help' for options.";
    }
}

// Handles "go <direction>". Only north leads anywhere from the cave mouth.
static String respondToGo(String direction) {
    if (direction.isEmpty()) {
        return "Go where?";
    }
    if (direction.equals("north")) {
        return "You walk north into the gloom.";
    }
    return "You can't go " + direction + " from here.";
}

split("\\s+", 2) — the regex and the limit

The first argument to split() is a regular expression, not a literal — \\s+ means "one or more whitespace characters", so any mix of spaces and tabs between the verb and noun collapses to one separator. The 2 is the limit: it caps the result at two elements, so only the first gap is a split point and "rusty key" survives intact as parts[1]. Without the limit, "take rusty key" would come back as three separate tokens and the item name would be truncated to "rusty".

The manual alternative: indexOf and substring

The same split without a regex:

int gap = input.trim().indexOf(' ');
String verb = gap < 0 ? input.trim() : input.trim().substring(0, gap);
String noun = gap < 0 ? "" : input.trim().substring(gap + 1);

indexOf(' ') returns the position of the first space, or -1 when there is none — always test for -1 before using the result. substring(start, end) takes characters from start up to but not including end; the single-argument substring(start) runs to the end of the string. It works, but split with a limit says the intent in one line.

String is immutable — parsing never changes the input

trim(), split(), substring(), toLowerCase() all return new String objects; the original is never touched. That's why the loop in Step 7 could safely normalize with trim().toLowerCase() without disturbing anything else holding that text. It's also why text is always compared with .equals(), never ==: == asks "the same object?", which is unreliable for strings built at runtime, while .equals() asks "the same characters?", which is what a command check actually means.

Step 11 — Enums: game states and directions

The command set has settled, so the string comparisons can become something the compiler checks. An enum is a type with a fixed, named set of values. Three of them earn their place here: the recognized verbs, the compass directions, and the game's overall state.

// The verbs the parser recognizes. UNKNOWN is the catch-all for anything else.
enum Verb {
    LOOK, GO, TAKE, INVENTORY, HELP, UNKNOWN;

    // Maps player text to a Verb, case-insensitively; UNKNOWN when nothing fits.
    static Verb fromInput(String text) {
        for (Verb v : values()) {
            if (v != UNKNOWN && v.name().equalsIgnoreCase(text)) {
                return v;
            }
        }
        return UNKNOWN;
    }
}

// The four compass directions. Parsing works the same way as Verb.
enum Direction {
    NORTH, SOUTH, EAST, WEST;

    static Direction fromInput(String text) {
        for (Direction d : values()) {
            if (d.name().equalsIgnoreCase(text)) {
                return d;
            }
        }
        return null;
    }
}

// Where the game stands. PLAYING keeps the loop running; QUIT and WON each
// end it with their own closing line.
enum GameState {
    PLAYING, QUIT, WON
}

With Verb in hand, respondTo()'s if/else if chain becomes a switch — one arm per constant, the default covering UNKNOWN:

static String respondTo(String command, Player player) {
    String[] parsed = parseCommand(command);
    Verb verb = Verb.fromInput(parsed[0]);
    String noun = parsed[1];

    switch (verb) {
        case LOOK:
            return caveDescription();
        case GO:
            return respondToGo(noun);
        case TAKE:
            return noun.isEmpty() ? "Take what?" : takeItem(player, noun);
        case INVENTORY:
            return describeInventory(player);
        case HELP:
            return helpText();
        default:
            return "You can't do that here. Type 'help' for options.";
    }
}

respondToGo() parses to a Direction and compares with == — safe now, because each constant is the only instance of itself:

static String respondToGo(String text) {
    if (text.isEmpty()) {
        return "Go where?";
    }
    Direction dir = Direction.fromInput(text);
    if (dir == null) {
        return "\"" + text + "\" isn't a direction.";
    }
    if (dir == Direction.NORTH) {
        return "You walk north into the gloom.";
    }
    return "You can't go " + dir.name().toLowerCase() + " from here.";

What an enum is — and why == is safe on one

Each constant in an enum is a single, permanent instance of that enum's type, created once by the JVM. There is exactly one Direction.NORTH in the whole program, so dir == Direction.NORTH is both correct and the idiomatic comparison — the reference-identity trap that makes == wrong for String doesn't exist here. The type is closed: Direction.UP doesn't compile, and neither does assigning a Direction variable anything outside the four listed names.

values(), name(), valueOf() — free on every enum

The compiler adds three members to every enum. values() returns an array of all its constants in declaration order — that's what both fromInput loops iterate. name() returns the constant's identifier as a String (Direction.NORTH.name() is "NORTH"). valueOf("NORTH") does the reverse, but throws IllegalArgumentException on any name that isn't a constant — which is exactly why fromInput rolls its own case-insensitive loop and returns a sentinel (null or UNKNOWN) instead of letting bad player input throw.

switch over an enum — no quotes, and a compiler that helps

Inside switch (verb) the case labels are the bare constant names — case LOOK, not case Verb.LOOK and not "look". Because the value set is closed, tools can flag a switch that forgets a constant, turning "handle the new command everywhere" into a checklist the compiler helps with rather than a runtime surprise. Each arm here ends in return, so there's no fall-through between cases; a switch that used break instead would need one per arm.

// A place the player can be. Every room names and describes itself; the two

    String name();
    String description();

    default String onEnter(Player player) {
        return "";

An interface is a contract; polymorphism is calling it blind

interface Room lists method signatures with no bodies (bar the two defaults). class Tunnel implements Room is a promise: "I provide every one of those." Code that holds a Room variable — or a Room[] mixing all three classes — can call description() or onEnter() on it without a single if checking the type. The JVM looks at the object's actual class at the moment of the call and runs that class's version. That indirection is polymorphism, and it's what lets a fourth room type be added later without touching respondToGo() at all.

default methods — write only what's different

An interface method with a body is a default: implementing classes inherit it and override only when they need something else. CaveMouth is a plain room, so it writes just name() and description() and takes the inherited onEnter() (returns "") and isExit() (returns false). Tunnel overrides onEnter(); UndergroundLake overrides isExit(). No class carries an empty return false; it doesn't care about — the default is the "don't care" answer.

Why the methods are public in the classes

Every member of an interface is implicitly public. A class can't implement an interface method with weaker visibility, so the methods in CaveMouth, Tunnel and UndergroundLake must be spelled public explicitly — leave it off and the method is package-private, and javac rejects the class for "attempting to assign weaker access privileges." The goldFound field, by contrast, is private: it's Tunnel's own bookkeeping and nothing outside it should see the flag flip.

Step 13 — Exceptions: handling bad input gracefully

Checked vs unchecked, and why GameException extends RuntimeException

An exception is an object thrown up the call stack until some catch handles it — or, if none does, the thread dies after printing a stack trace. Subclasses of RuntimeException are unchecked: methods that throw them need no throws clause and callers aren't forced to handle them. GameException extends RuntimeException so removeItemAt()'s signature stays clean and only the one place that can present a message — the DROP case — bothers to catch it. Extending Exception directly would make it checked, and every method in the call chain would need throws GameException bolted on.

One try, several catch — ordered specific to general

Integer.parseInt("banana") throws NumberFormatException; removeItemAt throws GameException. Both live in the same try, and each catch handles exactly one type, converting it to a return value the loop prints. When catch types share a hierarchy, the more specific one must come first — a catch (RuntimeException e) above catch (NumberFormatException e) won't compile, because the first would swallow everything and the second could never run. Here the two types are unrelated, so either order compiles, but specific-first is the habit to keep.

try-with-resources, and "look before you leap" vs "ask forgiveness"

try (Scanner in = new Scanner(System.in)) declares the resource in the parentheses; the JVM calls in.close() the instant the block exits, whether it falls off the end or an exception throws out of it. That's strictly better than the manual in.close() from Step 6, which a thrown exception would have jumped straight past. Note the game uses both risk styles deliberately: playLoop() still checks in.hasNextLine() before reading — cheap, obvious, do it up front — while DROP attempts the parse and catches the failure, because validating "is this a number?" by hand would just re-implement parseInt.

Step 14 — File I/O: saving and loading a game

A Player is now four things: health, gold, roomIndex, inventory. Write them to a text file and the player can quit and pick up where they left off. Keep the format plain key=value lines — a human can read it, and cat savegame.txt is a debugging tool. Imports first:

Two pure functions do the conversion, with no file anywhere in sight — which is what makes them testable:

static final Path SAVE_FILE = Path.of("savegame.txt");

// The player's state as a key=value text block.
static String toSaveText(Player player) {
    return "health=" + player.health + "\n"
         + "gold=" + player.gold + "\n"
         + "room=" + player.roomIndex + "\n"
         + "inventory=" + String.join(",", player.inventory) + "\n";
}

// The inverse: a fresh Player rebuilt from toSaveText()'s output.
static Player fromSaveText(String text) {
    Player player = new Player(100, 0);
    for (String line : text.split("\n")) {
        String[] kv = line.split("=", 2);
        if (kv.length < 2) {
            continue;
        }
        switch (kv[0]) {
            case "health": player.health = Integer.parseInt(kv[1]); break;
            case "gold": player.gold = Integer.parseInt(kv[1]); break;
            case "room": player.roomIndex = Integer.parseInt(kv[1]); break;
            case "inventory":
                if (!kv[1].isEmpty()) {
                    for (String item : kv[1].split(",")) {
                        player.inventory.add(item);
                    }
                }
                break;
        }
    }
    return player;
}

java.nio.file: Path names a file, Files does the work

Path.of("savegame.txt") is just a filename, resolved relative to the directory java was launched from — no file is touched until something acts on the path. Files.writeString(path, text) creates the file or truncates an existing one and writes the whole string in a single call; Files.readString(path) reads it all back. Both open and close the underlying stream internally, so there's nothing to close by hand — the older FileWriter/BufferedReader dance isn't needed for a file this size.

IOException is checked — the compiler makes you decide

IOException extends Exception, not RuntimeException, so it's checked: saveGame() and loadGame() must declare throws IOException, and every caller must then either catch it or declare it too. That's the language forcing an answer to "what happens when the disk is full, or the file is read-only, or it was deleted between check and read?" The SAVE/LOAD cases catch it and turn it into a line of game text; contrast Step 13's GameException, which is unchecked precisely so it doesn't impose this on every method it passes through.

Why LOAD copies fields instead of returning a new Player

respondTo(String command, Player player) receives a copy of the reference to the player — Java passes references by value. Writing player = loadGame(); inside respondTo() would only repoint that local copy; the playLoop() variable would still point at the old object. copyInto() sidesteps it by mutating the object the loop already holds — same reference, new field values. It's the same reason Step 8 threads the Scanner through as a parameter rather than expecting a reassignment to propagate back.

Step 15 — Collections: Map/Set for the world graph

Movement still does roomIndex++ for north and roomIndex-- for south — the layout is baked into arithmetic. A branching cave, or an east–west fork, can't be expressed that way. Model the world as what it actually is: a graph, stored as a Map from each room to its exits.

import java.util.HashSet;
import java.util.Map;
import java.util.Set;
// For each room index, which Direction leads to which other room index.
// A direction absent from a room's map is a wall. Map.of builds it immutable
// in one expression — the world never changes at runtime.
static final Map<Integer, Map<Direction, Integer>> WORLD = Map.of(
    0, Map.of(Direction.NORTH, 1),
    1, Map.of(Direction.NORTH, 2, Direction.SOUTH, 0),
    2, Map.of(Direction.SOUTH, 1)
);

Player gains a Set<Integer> visited, initialized to new HashSet<>() in the constructor with the starting room added: this.visited.add(0);.

Map — keys to values, and .get() returning null as a signal

A Map<K, V> associates each key with one value and looks it up in roughly constant time. WORLD nests two of them: room index → (direction → room index), which is exactly an adjacency list — the standard way to store a graph. get() returns null when the key isn't present, and the code leans on that twice: no entry for a direction means "wall". Map.of(...) creates a small immutable map inline; try to put() into it and it throws. That's the right default for fixed data — a mutable new HashMap<>() is for maps built up at runtime.

Set — no duplicates, and add() tells you if it was new

A Set holds each distinct element once. visited.add(destination) returns true when the element was actually inserted and false when it was already there — so boolean firstVisit = player.visited.add(...) both records the visit and answers "first time here?" in a single line. size() then counts distinct rooms seen, no matter how many times the player has paced back and forth. A HashSet gives fast membership with no ordering; TreeSet would keep the indices sorted, which isn't needed here.

Replacing branches with data

The old roomIndex++ / roomIndex-- hardcoded "north is the next room" into control flow, so every new room or non-linear connection meant new if branches. WORLD turns the layout into a value: it can be printed, unit-tested (as testWorldGraph() does), or one day read from a level file, and respondToGo() stays exactly as it is — only the map literal grows. "Prefer data over code" is why the Step 7 note about walls of if/else never came true.

Thirteen test<Name>() methods have accumulated, each ending in the same System.out.println(ok ? "[pass] ..." : "[fail] ..."). Collapse that repetition into one assertion helper with a running tally:

// Test bookkeeping. Each assertion calls check(); runTests() prints the total.
static int testsPassed = 0;

// Records one assertion. A failure prints its label so the line points
// straight at the check that broke.
static void check(boolean condition, String label) {
    if (condition) {
        testsPassed++;
    } else {

What the hand-rolled pattern buys, and what it costs

Upsides: zero dependencies, one compile, tests are just static methods you can read top to bottom, and java HelloWorld test works on any machine with a JDK. Downsides: runTests() is a call list you maintain by hand — forget a line and the test silently never runs; there's no isolation between tests, so leftover state could leak (these tests dodge it by building a fresh Player each time); and a test that throws instead of returning false aborts the entire run at that point. Fine for a single-file teaching project; it stops scaling somewhere around a second source file.

What JUnit adds on top

@Test discovery removes the call list — the runner finds every annotated method by reflection. Each test method runs on a fresh instance of the test class, so isolation is automatic. assertEquals(expected, actual) prints both sides on failure; assertThrows asserts that code throws; assertAll reports every failing assertion in a group instead of stopping at the first. @BeforeEach centralizes setup. A failure fails one method and the rest still run, and the output plugs into IDEs and CI. The price is the dependency and a classpath that can find it.

check() and assertEquals are the same idea

Both reduce "verify a fact, record the outcome" to a single call. The difference is mechanism: assertEquals throws an AssertionError that JUnit catches per method and tallies; check() just increments a counter and prints on failure. The habit you build writing check(actual.equals(expected), "why this matters") transfers directly — a JUnit test is the same assertions with a more capable runner underneath.

If the code used packages (package com.example.game;), those become directories inside the jar, mirroring the source tree; this single-file, package-less project just puts every class at the root.

Main-Class, and the trailing-newline trap

java -jar adventure.jar has to know which of the ten classes holds main(). The Main-Class: header in the manifest tells it; without one, java -jar stops with "no main manifest attribute." When you write MANIFEST.MF by hand, it must end with a newline — the manifest parser ignores a final line that has no line terminator, so a one-line file with no newline reads as empty and the header is silently lost. --main-class HelloWorld (or the classic jar cfe adventure.jar HelloWorld ..., where e is "entry point") sidesteps that by writing the header for you.

-d out, -C out ., and -jar vs -cp

javac -d out drops the .class files under out/ instead of beside the source, so the build output is one deletable directory. jar -C out . means "change into out, then add ." — so paths inside the jar are HelloWorld.class, not out/HelloWorld.class. At run time, java -cp out HelloWorld runs from the loose class files (what every earlier step effectively did with -cp .); java -jar adventure.jar runs from the bundle and takes its main class and classpath from the manifest, ignoring a -cp on the command line. The jar is the version you give to someone who just wants to play.

Step 18 — Ship it: the finished Java text adventure

Every earlier step lives in one file, HelloWorld.java: the greeting and its test from Steps 1–2, the Player class from Steps 3–4, Scanner input from Step 6, the game loop and methods from Steps 7–8, arrays and ArrayList from Step 9, command parsing from Step 10, three enums from Step 11, the Room interface and its implementations from Step 12, exceptions from Step 13, save/load from Step 14, the Map/Set world graph from Step 15, and the check() test runner from Step 16.

The complete HelloWorld.java 
import java.io.IOException;
import java.nio.file.Files;
import java.nio.file.Path;
import java.util.ArrayList;
import java.util.HashSet;
import java.util.Map;
import java.util.Scanner;
import java.util.Set;

public class HelloWorld {

    // The world's rooms, indexed 0..2. Fixed count, so a plain array.
    static final Room[] ROOMS = { new CaveMouth(), new Tunnel(), new UndergroundLake() };

    // The world graph: for each room index, which Direction leads where.
    // A missing direction is a wall. Immutable — the layout never changes.
    static final Map<Integer, Map<Direction, Integer>> WORLD = Map.of(
        0, Map.of(Direction.NORTH, 1),
        1, Map.of(Direction.NORTH, 2, Direction.SOUTH, 0),
        2, Map.of(Direction.SOUTH, 1)
    );

    // Where a saved game is written and read.
    static final Path SAVE_FILE = Path.of("savegame.txt");

    // ---- game text ----------------------------------------------------------

    // The game's opening greeting.
    static String greet() {
        return "Hello, World!";
    }

    // Prompts for the player's name and returns a welcome line. A blank
    // entry becomes "stranger". The Scanner is passed in so tests supply one.
    static String askName(Scanner in) {
        System.out.print("What is your name, adventurer? ");
        String name = in.nextLine().trim();
        if (name.isEmpty()) {
            name = "stranger";
        }
        return "Welcome, " + name + "!";
    }

    // The list of commands, shown by "help" and after any unknown command.
    static String helpText() {
        return "Commands: look, go <direction>, take <item>, drop <number>, "
             + "inventory, map, save, load, help, quit";
    }

    // ---- inventory --------------------------------------------------------

    // Adds an item to the player's pack and returns the line to show them.
    static String takeItem(Player player, String item) {
        player.inventory.add(item);
        return "You take the " + item + ".";
    }

    // A readable summary of what the player is carrying.
    static String describeInventory(Player player) {
        if (player.inventory.isEmpty()) {
            return "You are carrying nothing.";
        }
        return "You are carrying: " + String.join(", ", player.inventory);
    }

    // Removes and returns the item at a 1-based position, or throws a
    // GameException whose message is safe to show the player.
    static String removeItemAt(Player player, int position) {
        if (player.inventory.isEmpty()) {
            throw new GameException("Your pack is empty.");
        }
        if (position < 1 || position > player.inventory.size()) {
            throw new GameException("You have no item #" + position + ".");
        }
        return player.inventory.remove(position - 1);
    }

    // ---- rooms & movement ------------------------------------------------

    // The room the player is standing in right now.
    static Room currentRoom(Player player) {
        return ROOMS[player.roomIndex];
    }

    // Moves the player if the chosen direction has an exit, then reports the
    // new room and whatever entering it triggered.
    static String respondToGo(Player player, String text) {
        Direction dir = Direction.fromInput(text);
        if (dir == null) {
            return text.isEmpty() ? "Go where?" : "\"" + text + "\" isn't a direction.";
        }
        Integer destination = WORLD.get(player.roomIndex).get(dir);
        if (destination == null) {
            return "Solid rock blocks the way " + dir.name().toLowerCase() + ".";
        }
        player.roomIndex = destination;
        Room room = ROOMS[destination];
        boolean firstVisit = player.visited.add(destination);
        String body = firstVisit
                ? room.description()
                : "You are back at the " + room.name() + ".";
        String entering = room.onEnter(player);
        return entering.isEmpty() ? body : body + "\n" + entering;
    }

    // ---- save / load ---------------------------------------------------

    // The player's state as a key=value text block.
    static String toSaveText(Player player) {
        return "health=" + player.health + "\n"
             + "gold=" + player.gold + "\n"
             + "room=" + player.roomIndex + "\n"
             + "inventory=" + String.join(",", player.inventory) + "\n";
    }

    // A fresh Player rebuilt from toSaveText()'s output.
    static Player fromSaveText(String text) {
        Player player = new Player(100, 0);
        for (String line : text.split("\n")) {
            String[] kv = line.split("=", 2);
            if (kv.length < 2) {
                continue;
            }
            switch (kv[0]) {
                case "health": player.health = Integer.parseInt(kv[1]); break;
                case "gold": player.gold = Integer.parseInt(kv[1]); break;
                case "room": player.roomIndex = Integer.parseInt(kv[1]); break;
                case "inventory":
                    if (!kv[1].isEmpty()) {
                        for (String item : kv[1].split(",")) {
                            player.inventory.add(item);
                        }
                    }
                    break;
            }
        }
        return player;
    }

    static void saveGame(Player player) throws IOException {
        Files.writeString(SAVE_FILE, toSaveText(player));
    }

    static Player loadGame() throws IOException {
        return fromSaveText(Files.readString(SAVE_FILE));
    }

    // Copies loaded state into the Player the loop already holds, since
    // respondTo() can't reassign the caller's reference.
    static void copyInto(Player into, Player from) {
        into.health = from.health;
        into.gold = from.gold;
        into.roomIndex = from.roomIndex;
        into.inventory.clear();
        into.inventory.addAll(from.inventory);
    }

    // ---- command handling ---------------------------------------------

    // Splits a command line into a verb and the rest as its noun.
    static String[] parseCommand(String input) {
        String[] parts = input.trim().split("\\s+", 2);
        String verb = parts[0];
        String noun = parts.length > 1 ? parts[1] : "";
        return new String[] { verb, noun };
    }

    // Turns one command into the text shown to the player.
    static String respondTo(String command, Player player) {
        String[] parsed = parseCommand(command);
        Verb verb = Verb.fromInput(parsed[0]);
        String noun = parsed[1];

        switch (verb) {
            case LOOK:
                return currentRoom(player).description();
            case GO:
                return respondToGo(player, noun);
            case TAKE:
                return noun.isEmpty() ? "Take what?" : takeItem(player, noun);
            case DROP:
                try {
                    int position = Integer.parseInt(noun);
                    return "You drop the " + removeItemAt(player, position) + ".";
                } catch (NumberFormatException e) {
                    return "Drop which item? Use its number, e.g. \"drop 1\".";
                } catch (GameException e) {
                    return e.getMessage();
                }
            case INVENTORY:
                return describeInventory(player);
            case MAP:
                return "You have explored " + player.visited.size()
                     + " of " + ROOMS.length + " areas.";
            case SAVE:
                try {
                    saveGame(player);
                    return "Game saved.";
                } catch (IOException e) {
                    return "Couldn't save: " + e.getMessage();
                }
            case LOAD:
                try {
                    copyInto(player, loadGame());
                    return "Game loaded.\n" + currentRoom(player).description();
                } catch (IOException e) {
                    return "No saved game to load.";
                } catch (NumberFormatException e) {
                    return "Your save file is corrupt.";
                }
            case HELP:
                return helpText();
            default:
                return "You can't do that here. Type 'help' for options.";
        }
    }

    // ---- the loop -----------------------------------------------------

    // Reads commands until the player quits, wins, or input ends.
    static void playLoop(Scanner in, Player player) {
        GameState state = GameState.PLAYING;
        while (state == GameState.PLAYING) {
            System.out.print("> ");
            if (!in.hasNextLine()) {
                break;
            }
            String command = in.nextLine().trim().toLowerCase();
            if (command.equals("quit")) {
                state = GameState.QUIT;
            } else {
                System.out.println(respondTo(command, player));
                if (currentRoom(player).isExit()) {
                    state = GameState.WON;
                }
            }
        }
        System.out.println(state == GameState.WON
                ? "You climb into daylight. You have escaped the cave — you win!"
                : "Farewell, adventurer.");
    }

    // Runs one full play session against the given input source.
    static void startGame(Scanner in) {
        Player player = new Player(100, 0);
        System.out.println(greet());
        System.out.println(askName(in));
        System.out.println(currentRoom(player).description());
        System.out.println(takeItem(player, "torch"));
        playLoop(in, player);
    }

    public static void main(String[] args) {
        if (args.length > 0 && args[0].equals("test")) {
            runTests();
            return;
        }
        try (Scanner in = new Scanner(System.in)) {
            startGame(in);
        }
    }

    // ---- tests ------------------------------------------------------

    static int testsPassed = 0;
    static int testsFailed = 0;

    // Records one assertion; a failure prints its label.
    static void check(boolean condition, String label) {
        if (condition) {
            testsPassed++;
        } else {
            testsFailed++;
            System.out.println("[fail] " + label);
        }
    }

    static void testGreet() {
        check(greet().equals("Hello, World!"), "greet returns the greeting");
    }

    static void testAskName() {
        check(askName(new Scanner("Aria\n")).equals("Welcome, Aria!"), "askName greets by name");
        check(askName(new Scanner("\n")).equals("Welcome, stranger!"), "askName falls back to stranger");
    }

    static void testRespondTo() {
        Player player = new Player(100, 0);
        check(respondTo("look", player).startsWith("You stand at the mouth"), "look describes the cave mouth");
        check(respondTo("go north", player).contains("cramped tunnel"), "go north moves to the tunnel");
        check(respondTo("mumble", player).startsWith("You can't do that"), "an unknown verb is rejected");
    }

    static void testTakeItem() {
        Player player = new Player(100, 0);
        takeItem(player, "torch");
        takeItem(player, "rope");
        check(player.inventory.size() == 2, "takeItem adds to the pack");
        check(describeInventory(player).equals("You are carrying: torch, rope"), "describeInventory lists items");
    }

    static void testRoomsAreFixed() {
        check(ROOMS.length == 3 && ROOMS[0].name().equals("cave mouth"), "ROOMS is a fixed 3-room array");
    }

    static void testParseCommand() {
        String[] a = parseCommand("take rusty key");
        check(a[0].equals("take") && a[1].equals("rusty key"), "parseCommand splits verb and noun");
        check(parseCommand("look")[1].isEmpty(), "parseCommand gives an empty noun for one word");
    }

    static void testDirectionFromInput() {
        check(Direction.fromInput("north") == Direction.NORTH, "fromInput maps north");
        check(Direction.fromInput("EAST") == Direction.EAST, "fromInput is case-insensitive");
        check(Direction.fromInput("up") == null, "fromInput returns null for non-directions");
    }

    static void testVerbFromInput() {
        check(Verb.fromInput("take") == Verb.TAKE, "fromInput maps take");
        check(Verb.fromInput("wibble") == Verb.UNKNOWN, "fromInput returns UNKNOWN otherwise");
    }

    static void testRoomPolymorphism() {
        Player player = new Player(100, 0);
        Room tunnel = new Tunnel();
        String first = tunnel.onEnter(player);
        String second = tunnel.onEnter(player);
        check(first.contains("10 gold") && player.gold == 10, "Tunnel.onEnter grants gold once");
        check(second.isEmpty(), "Tunnel.onEnter is silent on re-entry");
        check(!new CaveMouth().isExit() && new UndergroundLake().isExit(), "only the lake overrides isExit");
    }

    static void testRemoveItemAt() {
        Player player = new Player(100, 0);
        takeItem(player, "torch");
        takeItem(player, "rope");
        check(removeItemAt(player, 1).equals("torch") && player.inventory.size() == 1, "removeItemAt drops by position");
        boolean threw = false;
        try {
            removeItemAt(player, 9);
        } catch (GameException e) {
            threw = true;
        }
        check(threw, "removeItemAt throws GameException on a bad index");
    }

    static void testSaveRoundTrip() {
        Player original = new Player(70, 25);
        original.roomIndex = 1;
        takeItem(original, "torch");
        takeItem(original, "map");
        Player restored = fromSaveText(toSaveText(original));
        check(restored.health == 70 && restored.gold == 25 && restored.roomIndex == 1, "save round-trip keeps scalars");
        check(restored.inventory.equals(original.inventory), "save round-trip keeps the inventory");
    }

    static void testWorldGraph() {
        check(WORLD.get(0).get(Direction.NORTH) == 1, "cave mouth leads north to the tunnel");
        check(WORLD.get(1).get(Direction.SOUTH) == 0, "the tunnel leads back south");
        check(WORLD.get(2).get(Direction.NORTH) == null, "the lake has no north exit");
    }

    static void testVisitedSet() {
        Player player = new Player(100, 0);
        boolean firstAdd = player.visited.add(1);
        boolean secondAdd = player.visited.add(1);
        check(firstAdd && !secondAdd, "Set.add reports whether the element was new");
        check(player.visited.size() == 2, "visited counts distinct rooms");
    }

    static void runTests() {
        testGreet();
        testAskName();
        testRespondTo();
        testTakeItem();
        testRoomsAreFixed();
        testParseCommand();
        testDirectionFromInput();
        testVerbFromInput();
        testRoomPolymorphism();
        testRemoveItemAt();
        testSaveRoundTrip();
        testWorldGraph();
        testVisitedSet();

        System.out.println(testsFailed == 0
                ? "All " + testsPassed + " checks passed."
                : testsPassed + " passed, " + testsFailed + " failed.");
    }
}

// A plain data class: the player's stats, position, pack and where they've been.
class Player {
    int health;
    int gold;
    int roomIndex;
    ArrayList<String> inventory;
    Set<Integer> visited;

    Player(int health, int gold) {
        this.health = health;
        this.gold = gold;
        this.roomIndex = 0;
        this.inventory = new ArrayList<>();
        this.visited = new HashSet<>();
        this.visited.add(0);
    }
}

// A place the player can be. Two default methods let a room opt in to an
// entry effect or to being the exit.
interface Room {
    String name();
    String description();

    default String onEnter(Player player) {
        return "";
    }

    default boolean isExit() {
        return false;
    }
}

class CaveMouth implements Room {
    public String name() {
        return "cave mouth";
    }
    public String description() {
        return "You stand at the mouth of a dark cave. A path leads north.";
    }
}

class Tunnel implements Room {
    private boolean goldFound = false;

    public String name() {
        return "tunnel";
    }
    public String description() {
        return "A cramped tunnel of dripping stone runs north and south.";
    }
    public String onEnter(Player player) {
        if (goldFound) {
            return "";
        }
        goldFound = true;
        player.gold += 10;
        return "You scoop up 10 gold coins from the tunnel floor.";
    }
}

class UndergroundLake implements Room {
    public String name() {
        return "underground lake";
    }
    public String description() {
        return "A still black lake fills the cavern. A climb north leads toward daylight.";
    }
    public boolean isExit() {
        return true;
    }
}

// Unchecked so it doesn't force a throws clause through every caller; its
// message is written to be shown to the player as-is.
class GameException extends RuntimeException {
    GameException(String message) {
        super(message);
    }
}

enum Verb {
    LOOK, GO, TAKE, DROP, INVENTORY, MAP, SAVE, LOAD, HELP, UNKNOWN;

    static Verb fromInput(String text) {
        for (Verb v : values()) {
            if (v != UNKNOWN && v.name().equalsIgnoreCase(text)) {
                return v;
            }
        }
        return UNKNOWN;
    }
}

enum Direction {
    NORTH, SOUTH, EAST, WEST;

    static Direction fromInput(String text) {
        for (Direction d : values()) {
            if (d.name().equalsIgnoreCase(text)) {
                return d;
            }
        }
        return null;
    }
}

enum GameState {
    PLAYING, QUIT, WON
}

What "the traditional Java way" actually meant

Nothing in this course touched a native compiler or an IDE. javac turned HelloWorld.java into JVM bytecode — portable, not machine code — and java ran that bytecode inside a JVM, which JIT-compiles hot methods to native code as the program runs. Debugging was jdb, the JDK's own command-line debugger (Step 5). Packaging was a jar — a ZIP of class files with a manifest (Step 17). The garbage collector reclaimed every Player, ArrayList and Room with no free anywhere. That's the whole toolchain: three commands that ship in every JDK, no build tool, no framework.

Where a real project goes from here

The single file is a teaching constraint, not a recommendation. A production version would split each class into its own file under a package, let a build tool (Maven or Gradle) manage the compile and pull in dependencies, move the hand-rolled check() tests to JUnit (Step 16), and add a proper save format instead of the key=value sketch from Step 14. The Java concepts underneath — classes, interfaces, enums, generics, collections, exceptions, the JVM — are exactly the same at that scale; only the tooling around them grows.
