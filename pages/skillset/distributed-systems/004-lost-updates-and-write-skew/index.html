Lost Updates, Check-Then-Act & Write Skew Prevention

Under READ_COMMITTED or even REPEATABLE_READ (Snapshot Isolation), two transactions can read the same set of rows, modify different rows, and break a cross-row business invariant (Write Skew—e.g., two doctors on call both clicking "go off shift" at the same instant). Prevent write skew using Isolation.SERIALIZABLE or by locking a shared parent/schedule row.

// BROKEN UNDER SNAPSHOT ISOLATION (Write Skew):
// Doctor Alice and Doctor Bob both see count(onCall) == 2, and both set their own row to false -> 0 doctors on call!
@Transactional(isolation = Isolation.REPEATABLE_READ)
public void leaveShiftBroken(UUID shiftId, UUID doctorId) {
    long activeDoctors = onCallRepo.countByShiftIdAndOnCallTrue(shiftId);
    if (activeDoctors <= 1) throw new IllegalStateException("At least one doctor must remain on call");
    onCallRepo.setOnCallFalse(shiftId, doctorId);
}

// PRODUCTION-SAFE: Materialize the conflict by locking the parent Shift row (or use Isolation.SERIALIZABLE)
@Transactional
public void leaveShiftSafe(UUID shiftId, UUID doctorId) {
    // 1. Lock the parent Shift row so concurrent shift changes serialize
    shiftRepo.findByIdForUpdate(shiftId).orElseThrow();

    // 2. Now the count and update execute under mutual exclusion
    long activeDoctors = onCallRepo.countByShiftIdAndOnCallTrue(shiftId);
    if (activeDoctors <= 1) {
        throw new IllegalStateException("Cannot leave shift: last doctor on call");
    }
    onCallRepo.setOnCallFalse(shiftId, doctorId);
}
