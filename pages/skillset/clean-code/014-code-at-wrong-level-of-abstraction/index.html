G6: Code at Wrong Level of Abstraction

Abstractions need a clean separation: high-level concepts belong in the base class or interface, and every low-level detail belongs in the derivatives. The two must never be mixed.
The tell is a general-purpose type that leaks a specific one — a Stack interface exposing percentFull(), a payment abstraction with a swipeMagneticStripe() method, a constant that only one implementation could ever care about. A reader of the abstraction is forced to learn about a detail that has nothing to do with the idea being modelled.
The fix is not to hide the detail; the detail is real. Move it down to the concrete type that actually owns it, so the abstraction states only what is true for all of its implementations.

Avoid — the interface leaks a detail only one implementation has
// Java
public interface Stack<T> {
    void push(T item);
    T pop();
    boolean isEmpty();

    // Only a fixed-size stack has a capacity — an unbounded one has no answer for this.
    double percentFull();
}

public class LinkedStack<T> implements Stack<T> {
    // ... push, pop and isEmpty are honest implementations ...

    @Override
    public double percentFull() {
        // Forced to implement a concept this stack does not have.
        return 0.0;
    }
}
Prefer — the abstraction holds only what every stack does
// Java
public interface Stack<T> {
    void push(T item);
    T pop();
    boolean isEmpty();
}

// Capacity is a property of a bounded stack, so it lives with the bounded stack.
public class BoundedStack<T> implements Stack<T> {
    private final int capacity;
    private int size;

    // ... push, pop and isEmpty ...

    public double percentFull() {
        return 100.0 * size / capacity; // percent, 0–100
    }
}

public class LinkedStack<T> implements Stack<T> {
    // ... push, pop and isEmpty, with no meaningless method to fake ...
}
