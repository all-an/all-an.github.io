Type-safe null elimination

A null reference makes every type secretly mean "or nothing", so the compiler cannot tell you where absence is possible — Tony Hoare called it his billion-dollar mistake. The fix is to put absence in the type: User means there is one, Optional<User> means there might not be.
Optional (Java 8+), Option<T> (Rust, Scala), Maybe (Haskell), T? and ?. (Kotlin). This is a runnable Maven project; see the README.md in this concept's folder in the cloned repository.

The return type states that the lookup can fail, and ofNullable converts null once at the boundary so nothing downstream sees one:

public Optional<User> find(String name) {
  return Optional.ofNullable(usersByName.get(name));   // null stops here
}

Steps that can each come up empty then compose flat — flatMap skips the empty case rather than testing for it, so the null checks are gone, not relocated:

public Optional<String> grandManagerOf(String name) {
  return find(name)
      .flatMap(User::managerName)
      .flatMap(this::find)
      .flatMap(User::managerName);
}

directory.grandManagerOf("carla").orElse("none");   // "ana", or "none" at any dead end

The caveat: in Java this is a library type, not a language one. Optional is not sealed, so no exhaustive switch forces you to handle empty, and get() on an empty one throws — moving an NPE rather than removing it. Kotlin's T? and Rust's Option<T> are checked by the compiler; Optional is a discipline the API encourages. Use it for return types, not fields or parameters.

Run the tests and the demo yourself with the Maven project — see the README.md in this concept's folder in the cloned repository.
