Single Responsibility Principle (SRP)

The S in SOLID: a class should have one reason to change. Not "do one thing" — the test is about people, not verbs. If the finance team and the ops team can both send you back to the same file for unrelated reasons, that file is answering to two masters and their changes will collide in it.

One reason to change in class design, a class per concern (Java, C#, Python, TypeScript), a focused module (Go, Rust), a service per role (DDD, microservices).

Three responsibilities in one class — the tax rules, the wire format, and the database. Each belongs to a different team, and each edit risks the other two:

class Invoice {
    Money total() { ... }               // finance changes the tax rules
    String toJson() { ... }             // the API team changes the wire format
    void save(Connection c) { ... }     // the DBA changes the schema
}

Split by who asks for the change, and each class has one caller to answer to:

class Invoice        { Money total() { ... } }          // finance
class InvoiceJson    { String format(Invoice i) { ... } }   // API
class InvoiceRepo    { void save(Invoice i) { ... } }       // persistence

The cost: "one reason" is a judgement, and applied too literally it produces a class per method — a graph of one-line collaborators where the logic is real but no single file explains it. The useful signal is empirical: which files keep appearing together in unrelated commits, and which class do two teams keep editing in the same week. Split on that evidence, not on a count of methods.
