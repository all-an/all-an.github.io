Open / Closed Principle (OCP)

Open for extension, closed for modification: adding a case should mean adding code, not editing working code. The test is the diff — if every new payment method reopens the same file, the file is not closed, and each edit re-risks the cases that already worked.

Abstract class or interface (Java, C#, Kotlin), trait (Rust, Scala, PHP), the strategy pattern, a plugin or extension point (ServiceLoader, MEF), sealed types plus pattern matching (Kotlin, Scala 3, Java 21).

A switch that grows forever. Every new method edits this method, and a forgotten branch is a runtime failure:

Money fee(Payment p) {
    switch (p.type()) {                        // reopened for every new type
        case CARD: return p.amount().times(0.029);
        case PIX:  return Money.ZERO;
        default:   throw new IllegalArgumentException();
    }
}

Behind an interface, the new case is a new file and the caller never changes:

interface Payment { Money fee(); }                                 // closed

record Card(Money amount) implements Payment {
    public Money fee() { return amount.times(0.029); }
}
record Boleto(Money amount) implements Payment {                   // added, nothing edited
    public Money fee() { return Money.of(3.50); }
}

The cost: closure is directional, and you only get it where you guessed right. Abstract over the wrong axis and every change still cuts across every implementation — now with indirection on top. It also trades one safety for another: an interface makes new types cheap and new operations expensive, since adding a method touches every implementor, while the switch is the reverse. When the set of cases is genuinely fixed, a sealed hierarchy with exhaustive pattern matching is the better answer — the compiler names every branch you missed.
