Module / namespace

A module does two jobs at once: it gives names a scope so util.Parser and http.Parser can coexist, and it decides what the outside world is allowed to see. Parnas (1972) argued the second is the point — a module should hide the decision most likely to change, exposing only an interface that survives it.

package (Java, Go, Python, Scala), mod (Rust), namespace (C++, C#), ns (Clojure).

In Java the package line creates the scope, and the missing modifier creates the interface — unmarked members are package-private, visible to neighbours but not to callers:

package http;

public class Parser { }    // the interface: visible everywhere
class Buffer { }           // package-private: an internal decision, free to change

// elsewhere
import http.Parser;        // import the name, not the whole path

JPMS adds a second layer on top: a package is invisible to other jars unless the module exports it, so public stops meaning "public to the world":

module com.example.http {
    exports http;          // http.Parser is reachable
                           // http.internal stays hidden, public or not
}

The trade-off: a namespace only prevents collisions, while encapsulation prevents coupling — and languages that give you the first for free (Python's _private convention, C++ headers) leave the second to discipline. If everything is public, you have folders, not modules.
