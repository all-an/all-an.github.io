Capability / permission system

In the object-capability model, authority is a reference. To be allowed to do something you must hold an unforgeable object that does it; there is no identity to check and no permission list to consult, because code that was never handed the object cannot express the request at all. This is the opposite of ambient authority — the design every mainstream language ships with, where Files.readString(path) is reachable from any line in the process and the only defence is asking who is calling. Under an ACL, a library you imported runs with all of your permissions; under capabilities it runs with exactly what you passed it. Capabilities are unforgeable (only obtainable by being given one), attenuable (derive a weaker one to hand on), delegable (authority travels with the reference) and revocable (withdraw a grant after the fact). Here an untrusted plugin gets a read-only view of one directory, and can do precisely that and nothing else.

"No ambient authority" is a structural property, not a rule anyone follows. The resource is unreachable: the store is never handed out, only a capability that closes over it, and it comes into existence together with the single root reference that can reach it — the way an operating system hands a fresh process its initial capabilities. There is no static accessor to call and no registry to look in:

public final class FileStore {

  private final Map<String, String> files = new LinkedHashMap<>();

  // Private: a store can only come into existence together with its root capability.
  private FileStore() {
  }

  // Create a store and return the *only* reference that can reach it — the root of
  // all authority over it. Every narrower capability is derived from this one;
  // authority can be given away and narrowed, but never conjured up.
  public static FileAccess createWithRootAccess() {
    return new RootAccess(new FileStore());
  }

  // Private and final, so no other code can build one — capabilities are
  // *unforgeable*. The only way to hold one is to be given it.
  private record RootAccess(FileStore store) implements FileAccess { /* ... */ }
}

Attenuation derives a weaker capability from one you hold — least privilege by construction rather than by policy. The subtle part is that narrowing must produce a genuinely different object, not the same one seen through a narrower interface: if FileAccess were a subtype of ReadAccess, anyone given the "read-only" view could cast it straight back to full authority. That is why the two interfaces are deliberately unrelated:

// Drop the authority to write, keeping the authority to look. The result is a
// genuinely different object of a type that has no write method — not the same
// object viewed through a narrower interface, which the holder could cast back.
public static ReadAccess readOnly(FileAccess full) {
  return new ReadOnlyView(full);
}

// Forwards only reads. Private and final: nobody outside can construct one, and
// it does not implement FileAccess, so `(FileAccess) readOnlyCapability` fails.
private record ReadOnlyView(FileAccess full) implements ReadAccess {

  @Override
  public String read(String path) {
    return full.read(path);
  }
}

Scoping narrows differently — still full read/write authority, but only within a subtree. Note what the check does not do: it never asks who is calling. The answer depends only on which capability was used, so the same code invoked by anyone gets the same result. An attenuated capability also refuses to reveal what lies outside it, since a listing is information too:

private String checkInScope(String path) {
  if (!path.startsWith(pathPrefix)) {
    throw new SecurityException("outside this capability's scope: " + path);
  }
  return path;
}

// Only the paths this view can reach — an attenuated capability must not even
// reveal what lies outside it.
@Override
public Set<String> list() {
  return full.list().stream()
      .filter(path -> path.startsWith(pathPrefix))
      .collect(Collectors.toUnmodifiableSet());
}

Delegation is just passing the reference — and it makes authority legible. Everything this untrusted plugin can reach arrives through its constructor, so a reader can establish its full powers from the call site without reading a line of its body:

public final class Plugin {

  private final ReadAccess files;   // the entirety of its authority over the world

  public Plugin(ReadAccess files) {
    this.files = files;
  }
}

// At the call site, the plugin's complete authority is visible in one expression:
Plugin plugin = new Plugin(Attenuation.readOnly(Attenuation.scopedTo(root, "/home/")));

Revocation is the hard one: a reference handed away is gone, and you cannot reach into another component to take it back. The caretaker pattern (Redell, 1974) solves it by never handing over the real capability — you give out a forwarder you can switch off. The essential move is that this splits one capability into two that go to different places: the grantee gets access(), the grantor keeps the caretaker and with it the power to revoke():

// Held privately and dropped on revocation. Nulling it is what makes revocation
// real: afterwards no path from the forwarder reaches the resource, whatever the
// grantee still has a reference to.
private ReadAccess target;

// Created once, so the grantee holds the same object before and after revocation.
// Its authority changes underneath it; the reference does not.
private final ReadAccess forwarder = new Forwarder();

public ReadAccess access() { return forwarder; }

public void revoke() { target = null; }

The tests pin the defining properties — narrowing cannot be undone, delegation carries authority with the reference, and a grant can be cut off after it was handed over without damaging the capability it came from:

@Test
void readOnlyCapabilityCannotBeCastBackToFullAccess() {
  ReadAccess readOnly = Attenuation.readOnly(root);

  assertEquals("hunter2", readOnly.read("/etc/secrets.txt"));
  assertFalse(readOnly instanceof FileAccess);
}

@Test
void revocationCutsOffACapabilityAlreadyHandedOver() {
  Caretaker caretaker = Caretaker.forwarding(Attenuation.readOnly(root));
  ReadAccess granted = caretaker.access();
  assertEquals("hunter2", granted.read("/etc/secrets.txt"));

  caretaker.revoke();

  assertThrows(SecurityException.class, () -> granted.read("/etc/secrets.txt"));
}

One assertion is deliberately missing: there is no test that the granted reference is not a Caretaker, because it cannot be written — caretaker.access() instanceof Caretaker is a compile error, since a ReadAccess provably can never be that unrelated final type. The compiler rules it out before the code can exist, which is a stronger guarantee than any test could give. That is capability design working as intended: the safety property becomes something the type system enforces rather than something a check catches at run time.

Where this shows up for real. Every piece of this project has a counterpart in software you have already used:

FileStore.createWithRootAccess()   the fds a process is handed at exec;
                                   the host passing handles into a wasm module
Attenuation.scopedTo(root, "/home/")   wasmtime --dir=/tmp; openat(dirfd, ...);
                                       an S3 policy scoped to a key prefix
Attenuation.readOnly(...)          open(O_RDONLY); Deno's --allow-read=/tmp;
                                   an OAuth token carrying only a read scope
Caretaker.revoke()                 OAuth revocation endpoints; session
                                   invalidation; short-TTL STS credentials

The clearest everyday example is the Unix file descriptor, which is already a capability: unforgeable (an index into a kernel table you cannot fabricate), attenuable (O_RDONLY), and genuinely delegable — you can pass one to another process over a Unix socket with SCM_RIGHTS. What spoils it is open(), which takes a path and checks who you are: ambient authority, right in the middle of an otherwise capability-shaped design. FreeBSD's Capsicum removes exactly that. After cap_enter() the process is confined: path-based open() stops working entirely, and files can only be reached through a directory descriptor already held. That is the same move as making this project's FileStore constructor private — delete the ambient entry point, and confinement becomes structural rather than checked:

cap_enter();                              // no more ambient authority, ever

open("/etc/passwd", O_RDONLY);            // ECAPMODE — the path names nothing now
openat(home_fd, "notes.txt", O_RDONLY);   // fine: derived from a held capability

WASI is the cleanest mainstream deployment of the model, and it matches this code almost line for line. A WebAssembly module starts with zero ambient authority — it cannot open a file, because no reachable call takes a path out of nowhere. The host preopens directories and passes the handles in, so the module reaches /tmp and nothing else, not because a check rejects other paths but because it holds no handle that names them:

wasmtime --dir=/tmp app.wasm    # this is literally Attenuation.scopedTo

The practical stakes are clearest in the supply chain. When the event-stream npm package was compromised in 2018, the injected payload could read the filesystem and exfiltrate wallet keys — not by defeating any check, but because in Node every transitive dependency runs with the full authority of the process. This is the confused deputy at scale, and identity checks are powerless against it: the malicious code genuinely is you. Deno's --allow-read=/tmp and Node's permission model are retrofits of precisely this concept, imperfect for the reason below — one ambient back door undoes the property — but capability-shaped in direction.

You have likely done this in ordinary application code without naming it: injecting a ReadOnlyUserRepository instead of the full UserRepository is attenuation, with the narrow type as the capability. The failure mode is the familiar one too — if UserRepository extends ReadOnlyUserRepository, the "read-only" collaborator can cast straight back to the writable one, which is exactly the bug the two unrelated interfaces above exist to prevent. Be honest about the limit, though: in Java this is a convention, not a guarantee. Reflection defeats it, and any static Files call or unguarded singleton is an ambient back door. It buys legibility and accident-prevention, not defence against hostile code sharing your process.

Why bother: as the supply-chain case above shows, it dissolves the confused deputy problem — a component's authority is bounded by what was passed to it, visible at the call site, and auditable without reading its body. It also makes least privilege the default: you cannot accidentally grant more than you meant to, because granting is an explicit act. The trade-offs: it must be pervasive to be worth much — one ambient back door (a static file API, reflection, an unguarded singleton) undoes it, which is why retrofitting capabilities onto an existing language is so hard and why Java's SecurityManager was deprecated rather than fixed. Passing capabilities explicitly is also more plumbing than calling a global, revocation costs an indirection per grant, and answering "who can reach this file?" becomes hard precisely because there is no central list to consult.
