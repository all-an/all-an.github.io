Bytecode / IR

An intermediate representation is a language in the middle: not the source anyone writes, not the machine code anything executes, but a flat instruction set both sides agree on. A compiler frontend lowers source to it; a backend turns it into something that runs. The payoff is decoupling — with M languages and N targets you write M + N pieces instead of M × N, and every new backend works for every existing language for free. Bytecode is an IR designed to be executed directly by a virtual machine, usually a stack machine: operands live on an operand stack, so instructions are compact and trivial to generate. Being flat also makes it verifiable — stack depth and well-formedness can be checked by walking the code once, before it runs. Here two unrelated source languages lower to one instruction list, which is then both executed and translated.
JVM bytecode (Java / Kotlin / Scala / Clojure), LLVM IR (C / C++ / Rust / D), WASM (polyglot), CLR IL (C# / F#), BEAM bytecode (Erlang / Elixir). This is a runnable Maven project; see the README.md in this concept's folder in the cloned repository.

The source is a nested expression tree — convenient to parse, but not something a machine executes directly. Lowering walks it in post-order: both operands are emitted before the operation that consumes them, so by the time that operation runs its inputs are already on the stack. The tree's nesting becomes an ordering — that is the whole lowering:

private static void emit(Expr expr, List<Instruction> code) {
  switch (expr) {
    case Expr.Literal literal -> code.add(new Instruction.Push(literal.value()));
    case Expr.Variable variable -> code.add(new Instruction.Load(variable.name()));
    case Expr.BinaryOp binary -> {
      emit(binary.left(), code);    // left first — this fixes the operand order
      emit(binary.right(), code);
      code.add(binary.op());        // ...then the operation that consumes both
    }
  }
}

// 3 * x + 7   lowers to:   [push 3, load x, mul, push 7, add]

A second frontend — reverse Polish notation text, a language sharing nothing with the tree — lowers to the identical instruction list. RPN is already written in the order a stack machine wants, so each token becomes exactly one instruction. Two languages, one representation, and everything downstream is shared:

for (String token : source.trim().split("\\s+")) {
  code.add(switch (token) {
    case "+" -> Arith.ADD;
    case "-" -> Arith.SUB;
    case "*" -> Arith.MUL;
    // Anything else is a literal if it parses as a number, or a variable name.
    default -> token.matches("-?\\d+")
        ? new Instruction.Push(Integer.parseInt(token))
        : new Instruction.Load(token);
  });
}

// "3 x * 7 +"  lowers to:  [push 3, load x, mul, push 7, add]   — the same list

Backends consume that list without knowing which language produced it. One executes it on an operand stack — this is what a bytecode interpreter is; the JVM, the CLR and a WASM runtime do exactly this with a bigger instruction set. Note the pop order: the right operand was emitted last, so it sits on top, and reversing it would silently compute 4 - 10 for 10 - 4:

for (Instruction instruction : code) {
  switch (instruction) {
    case Instruction.Push push -> stack.push(push.value());
    case Instruction.Load load -> stack.push(environment.get(load.name()));
    case Arith arith -> {
      int right = stack.pop();   // emitted last, so it is on top
      int left = stack.pop();
      stack.push(arith.apply(left, right));
    }
  }
}

The other backend translates the same list to source text instead of running it — identical algorithm, but the "values" are fragments of source, so the tree the frontend flattened is reconstructed as text. A second target costs one new backend, not one new compiler per language; this is how LLVM IR is lowered to x86, ARM or WASM by swapping backends:

case Arith arith -> {
  String right = stack.pop();
  String left = stack.pop();
  stack.push("(" + left + " " + arith.symbol() + " " + right + ")");
}

// [push 3, load x, mul, push 7, add]  ->  "((3 * x) + 7)"

Because the list is flat with a fixed stack effect per instruction, it can be verified statically — no inputs, no execution. The walk also yields the deepest the stack will ever get, which is exactly what the JVM records as a method's max_stack so the frame can be sized before entry:

for (Instruction instruction : code) {
  // An operation consumes two operands and leaves one: net -1. Anything else: +1.
  if (instruction instanceof Arith) {
    if (depth < 2) throw new IllegalArgumentException("stack underflow at `" + instruction.text() + "`");
    depth--;
  } else {
    depth++;
  }
  maxDepth = Math.max(maxDepth, depth);
}

// A well-formed expression leaves exactly its one result behind.
if (depth != 1) throw new IllegalArgumentException("code must leave exactly 1 value");

The tests pin the defining properties — unrelated frontends converge on one representation, every backend consumes it without knowing its origin, operand order survives the flattening, and malformed code is rejected before it runs:

@Test
void unrelatedFrontendsProduceTheSameIr() {
  assertEquals(ExprCompiler.compile(tree()), RpnCompiler.compile("3 x * 7 +"));
}

@Test
void oneIrFeedsSeveralBackends() {
  List<Instruction> code = ExprCompiler.compile(tree());
  assertEquals(22, StackMachine.run(code, Map.of("x", 5)));
  assertEquals("((3 * x) + 7)", SourceEmitter.emit(code));
}

@Test
void verifierRejectsStackUnderflow() {
  assertThrows(IllegalArgumentException.class, () -> StackMachine.verify(List.of(Arith.ADD)));
}

Why bother: the IR is the seam that makes a toolchain tractable. Languages and targets evolve independently — Kotlin and Clojure got the JVM's optimizer and GC for free by emitting its bytecode, and Rust got every LLVM backend the same way. It is also where optimization lives: a pass written against the IR improves every language at once. And a flat, verifiable format is what makes running untrusted code plausible at all, which is the whole premise of the JVM sandbox and of WASM in a browser. The trade-offs: an IR is a lowest common denominator — it must be general enough for every frontend, so language-specific meaning gets erased on the way down and is hard to recover later (which is why generic type information and other source-level detail is famously thin in bytecode). Lowering also costs a compilation stage, and a stack machine's compactness is paid for in dispatch: real engines JIT the bytecode to registers precisely to win that back.
