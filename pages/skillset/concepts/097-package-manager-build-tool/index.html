Package manager / build tool

You declare what you depend on; the tool resolves the graph, fetches it, and compiles in the right order. The hard part is never the download — it is that your dependencies have dependencies, and two of them will eventually want different versions of the same thing.

Maven / Gradle (Java, Scala), sbt (Scala), Cargo (Rust), npm (JavaScript), pip (Python), go mod (Go).

A coordinate is groupId:artifactId:version — the namespace that keeps two Parser jars apart — and scope keeps test-only code out of what you ship:

<dependency>
  <groupId>org.junit.jupiter</groupId>
  <artifactId>junit-jupiter</artifactId>
  <version>5.10.2</version>
  <scope>test</scope>      <!-- on the test classpath only -->
</dependency>

Transitive dependencies arrive uninvited, so the real question is which version won:

mvn dependency:tree

[INFO] com.example:app:jar:1.0
[INFO] +- org.apache.httpcomponents:httpclient:jar:4.5.14:compile
[INFO] |  \- commons-codec:commons-codec:jar:1.11:compile   # you never asked for this
[INFO] \- org.junit.jupiter:junit-jupiter:jar:5.10.2:test

The conflict: SemVer says 1.11 and 1.15 are compatible, but one classloader can hold only one commons-codec. Maven picks the version nearest the root of the tree — shortest path wins, not highest number — which is why an unrelated upgrade can silently downgrade a transitive dependency. Cargo sidesteps it by linking both copies; on the JVM you pin the winner with <dependencyManagement> or shade the jar.
