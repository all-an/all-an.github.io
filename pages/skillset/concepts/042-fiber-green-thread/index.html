Fiber / green thread

A fiber (green thread) is a unit of execution scheduled by a language runtime instead of the operating system. The runtime multiplexes M fibers onto N carrier OS threads — that mapping is what M:N scheduling means, and N normally defaults to the CPU count. A fiber costs a few hundred bytes of heap, not the ~1 MB stack the kernel reserves for every platform thread, so one process can hold millions of them instead of thousands.
In Java this is Project Loom's virtual thread; Go calls it a goroutine, Erlang a process, ZIO a fiber, Tokio a task. The payoff is that thread-per-task stops being expensive: you can write plain blocking code and still serve 100 000 concurrent connections, with no pool sizing and no callback rewriting.
This page is about the mapping — how many tasks the runtime can hold at once. Its counterpart, Coroutine / green thread, is about the mechanism inside a single task: how one of them pauses and resumes.

// Java
import java.time.Duration;
import java.util.Set;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.Executors;
import java.util.concurrent.atomic.AtomicInteger;

// Each task records the carrier OS thread that ran it, which makes the M:N ratio visible.
Set<String> carriers = ConcurrentHashMap.newKeySet();
AtomicInteger finished = new AtomicInteger();

// One virtual thread per task: 10 000 tasks, each blocked on slow I/O for 200 ms.
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
  for (int task = 0; task < 10_000; task++) {
    executor.submit(() -> {
      // A mounted virtual thread prints as "VirtualThread[#31]/runnable@<carrier name>".
      String label = Thread.currentThread().toString();
      carriers.add(label.substring(label.indexOf('@') + 1));

      // Blocking here unmounts the fiber and hands its carrier to another waiting task.
      Thread.sleep(Duration.ofMillis(200));

      finished.incrementAndGet();
      return null;
    });
  }
} // close() blocks until every submitted task has completed

System.out.println(finished.get() + " tasks ran on " + carriers.size() + " carrier threads");
// 10000 tasks ran on 10 carrier threads   <- M = 10 000, N = 10: that is the M:N ratio
// Wall time stays near 200 ms, because the 10 000 waits overlap instead of queueing.

// The same shape with platform threads asks the kernel for 10 000 stacks of about 1 MB each:
// Executors.newFixedThreadPool(10_000) reserves gigabytes and usually ends in OutOfMemoryError.
// JavaScript
const TASK_COUNT = 10_000;

// Sleeping without blocking: the timer resumes this task later, from the event-loop queue.
const sleep = (milliseconds) => new Promise((resume) => setTimeout(resume, milliseconds));

let finished = 0;

// One unit of work, same as the Java task above: wait 200 ms, then count itself.
async function slowTask() {
  await sleep(200);
  finished += 1;
}

async function main() {
  const startedAt = Date.now();

  // 10 000 tasks in flight at once, each a small heap object instead of an OS thread stack.
  const tasks = [];
  for (let task = 0; task < TASK_COUNT; task += 1) {
    tasks.push(slowTask());
  }
  await Promise.all(tasks);

  console.log(`${finished} tasks ran on 1 event-loop thread in ${Date.now() - startedAt} ms`);
}

main();
// 10000 tasks ran on 1 event-loop thread in 271 ms

// JavaScript takes the same idea to its extreme: N = 1. Every wait still overlaps, but a
// CPU-bound task has no second carrier to yield to, which is what Java's N > 1 buys you.
