FFI / foreign function interface

Linking finds the function; the FFI is what happens at the call itself. Two languages disagree about where arguments live, who cleans up the stack, how a string is laid out and who owns the memory afterwards — the FFI is the translation layer that makes one side's calling convention acceptable to the other.

Panama FFM API (Java 22+), JNI (legacy Java), cgo (Go), ctypes (Python), extern "C" (Rust, C++), P/Invoke (C#).

Panama describes the C signature as data — strlen(const char*) -> size_t becomes a FunctionDescriptor, and the linker builds a call stub from it, with no C glue to write or compile:

Linker linker = Linker.nativeLinker();
MethodHandle strlen = linker.downcallHandle(
    linker.defaultLookup().find("strlen").orElseThrow(),
    FunctionDescriptor.of(ValueLayout.JAVA_LONG, ValueLayout.ADDRESS));

The other half is memory. An Arena owns the off-heap copy of the string and frees it at the end of the block — the lifetime is scoped, not left to the GC, which knows nothing about it:

try (Arena arena = Arena.ofConfined()) {
    MemorySegment cString = arena.allocateFrom("hello");   // NUL-terminated, off-heap
    long len = (long) strlen.invoke(cString);              // 5
}   // freed here; using cString afterwards throws, it does not corrupt

The cost: every crossing is a boundary the compiler cannot see through — no inlining, no escape analysis, and a GC that must not move an object the native side is holding. Get a descriptor wrong and there is no type error, just a mismatched stack frame and a JVM crash. JNI paid that price in hand-written C and manual pinning; Panama moves the description into Java and the lifetime into Arena, but the boundary itself stays expensive — batch across it, do not chatter.
