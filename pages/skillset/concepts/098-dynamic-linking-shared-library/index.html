Dynamic linking / shared library

Static linking copies the library into your binary at build time. Dynamic linking leaves a hole and a name, and the loader fills it when the program starts — so one copy of libssl in memory serves every process, and patching it does not mean rebuilding them. The cost is that the dependency is no longer inside the artifact you tested.

.so (Linux), .dylib (macOS), .dll (Windows); dlopen (C, Rust), System.loadLibrary (Java), ctypes (Python).

In Java the load is explicit and deferred to a static initializer — the JVM searches java.library.path for libimaging.so and binds the native methods only when the class is first used:

public class Imaging {

    static {
        System.loadLibrary("imaging");   // libimaging.so / .dylib / imaging.dll
    }

    private static native long openImage(String path);   // no body: it lives in the library
}

Nothing verifies the library is there until that moment, so a missing or mismatched file is a runtime failure, never a compile-time one:

java -Djava.library.path=/opt/imaging/lib -jar app.jar

Exception in thread "main" java.lang.UnsatisfiedLinkError: no imaging in java.library.path

The trade-off: shared libraries only stay shareable while the ABI holds — struct layouts, symbol names and calling conventions are the contract, not the source. Change a field's order and every caller compiled against the old header reads garbage, which is why libraries carry a soname (libssl.so.3) and why "DLL hell" is a versioning problem, not a linking one. Static linking trades disk and patchability for knowing exactly what you shipped — the reason Go and GraalVM native images default to it.
