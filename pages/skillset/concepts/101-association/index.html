Association

The weakest structural link between two classes: one keeps a reference to the other. No ownership, no lifecycle claim — but the reference is a field, so it survives between calls, which is what separates this from a dependency and its parameter that vanishes when the method returns. It is the base case of the structural relationships; aggregation and composition are associations that also say something about who owns what.

A field reference (Java, C#, Python), a solid line in UML notation, uses-a in general OOP, unidirectional or bidirectional.

Unidirectional: the order knows its customer, the customer knows nothing about orders. One arrow, one field, one direction of navigation:

class Order {
    private final Customer customer;   // Order ──> Customer

    Order(Customer customer) { this.customer = customer; }
}

Bidirectional means both ends navigate — and both ends must now be kept in step, which is why one side has to own the update:

class Customer {
    private final List<Order> orders = new ArrayList<>();

    void addOrder(Order order) {       // single point that maintains both ends
        orders.add(order);
        order.setCustomer(this);
    }
}

The cost: a bidirectional association is two facts that can disagree. Set one side directly and the graph is inconsistent — an order pointing at a customer whose list does not contain it. It also creates a cycle: naive serialization loops forever, and equals/hashCode that follow both ends recurse. Prefer unidirectional, and add the back-reference only when a real query needs it.
