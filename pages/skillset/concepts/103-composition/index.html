Composition

The strong whole-part relationship: the whole creates its parts, is the only thing that references them, and takes them down with it. A part belongs to exactly one whole and has no meaning outside it — an order line without its order is nothing, so its lifetime is not a separate question.

Owned lifecycle (Java, C#, C++), a filled diamond in UML notation, owns-a in general OOP, unique_ptr<T> / Box<T> (C++, Rust) — the part dies with the whole.

The parts are built inside, from plain data. No caller ever holds a reference to one, so no caller can outlive the whole while pointing into it:

class Order {
    private final List<OrderLine> lines = new ArrayList<>();   // Order ◆──> OrderLine

    void add(Product product, int quantity) {
        lines.add(new OrderLine(product, quantity));            // created here, never passed in
    }
}

C++ and Rust make the claim in the type: a unique_ptr member cannot be copied out, and destroying the whole runs the part's destructor:

class Engine;

class Car {
    std::unique_ptr<Engine> engine;   // sole owner
public:
    Car() : engine(std::make_unique<Engine>()) {}
};                                    // ~Car() destroys the Engine — nothing else can hold it

The cost: the invariant only holds while the part stays private. Return the internal list or the part itself and you have quietly turned composition into aggregation — the caller now holds something whose lifetime you claimed to control. So expose copies or read-only views, and keep the part's construction inside the whole; the moment a part is passed in from outside, its lifetime belongs to whoever created it.
