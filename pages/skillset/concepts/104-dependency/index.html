Dependency

The weakest relationship of the four: one class mentions another without keeping it. No field, no lifetime, nothing to maintain between calls — the reference exists for the duration of a method and then is gone. It is still a coupling, because changing the other class's signature breaks this one, but it is coupling to a name rather than to an object.

A constructor or method parameter (Java, C#, Python), a local variable, a return type, a thrown exception, a static call — a dashed arrow in UML notation.

Invoice depends on TaxRate and Money, but stores neither. Both are gone when the method returns:

class Invoice {
    Money total(TaxRate rate) {          // Invoice ┄┄> TaxRate (parameter)
        Money net = sumOfLines();        // Invoice ┄┄> Money (local + return)
        return net.plus(rate.applyTo(net));
    }
}

Which is why the dependency can be aimed at an abstraction and swapped per call — the same method works against anything satisfying the interface:

void print(Report report, Formatter formatter) {   // depends on the interface, not a class
    System.out.println(formatter.format(report));
}

print(report, new JsonFormatter());
print(report, new CsvFormatter());

The cost: it is invisible in a field list, so it accumulates unnoticed — a class with three fields can still name twenty types across its method signatures, and every one of them is a reason to recompile and a thing a test must supply. Static calls and new inside a method are the same coupling with no seam to substitute at. Keep parameter dependencies pointed at interfaces, and count them: a long parameter list is usually a missing object.
