Liskov Substitution Principle (LSP)

Barbara Liskov's rule (1987): anywhere the program expects a type, any subtype must work without the caller noticing. Compiling is not enough — the subtype has to keep the promises, not just the signatures. A subclass may accept more and guarantee more, never the reverse.

Subtype substitutability (all OOP languages), covariant return (Java, C#, Kotlin), contravariant parameters (Kotlin, Scala, TypeScript), sealed hierarchies (Kotlin, Java 17+, Scala 3).

The classic break. Rectangle promises that width and height move independently; Square cannot keep that promise, because its invariant forces the other side to follow:

class Rectangle {
    protected int width, height;
    void setWidth(int w)  { this.width = w; }
    void setHeight(int h) { this.height = h; }
    int area() { return width * height; }
}

class Square extends Rectangle {
    void setWidth(int w)  { this.width = w; this.height = w; }   // keeps the sides equal
    void setHeight(int h) { this.width = h; this.height = h; }   // — and silently breaks the base promise
}

The caller was written against Rectangle and knows nothing about squares. It passes for the base type and fails for the subtype — setHeight(4) has quietly reset the width to 4:

void resize(Rectangle r) {
    r.setWidth(5);
    r.setHeight(4);
    assert r.area() == 20;   // Rectangle: 5 × 4 = 20 ✓   Square: 4 × 4 = 16 ✗
}

The fix is to stop inheriting a promise you cannot keep. Share only what both types actually agree on — an area — and drop the mutators that caused the conflict, so there is no independent width to contradict:

sealed interface Shape permits Rectangle, Square {
    int area();
}

record Rectangle(int width, int height) implements Shape {
    public int area() { return width * height; }
}
record Square(int side) implements Shape {     // no longer a Rectangle — nothing to violate
    public int area() { return side * side; }
}

Resizing becomes a function that returns a new value, and each type states its own rule. The caller gets back what it asked for, whichever type it held:

Shape resized = switch (shape) {
    case Rectangle r -> new Rectangle(5, 4);   // 20
    case Square s    -> new Square(4);         // 16, and the caller was told it is a square
};

The other two breaks are the same rule from either side — refusing input the base accepts, or throwing where the base returns:

class Base    { void put(Object o) { ... } }
class Strict extends Base {
    void put(Object o) {
        if (!(o instanceof String)) throw new IllegalArgumentException();   // narrowed the input
    }
}

class ReadOnlyList extends ArrayList<String> {
    public boolean add(String s) { throw new UnsupportedOperationException(); }   // withdrew a promise
}

The cost: nothing checks this. The compiler verifies types; preconditions, postconditions and invariants live in prose, so a violation shows up as a caller failing on a subtype it never heard of. The practical guard is to run the base type's tests against every subtype, and to treat an instanceof check in a caller as the diagnosis: if code must ask which subtype it holds, substitution has already failed. When behaviour genuinely differs, prefer composition or a sealed hierarchy over inheritance.
