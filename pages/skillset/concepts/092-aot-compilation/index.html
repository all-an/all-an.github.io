AOT compilation

Ahead-of-time (AOT) compilation translates a whole program to machine code at build time, before it is ever run. It is the opposite trade to a JIT: a JIT ships the source, starts interpreted, profiles what runs hot and compiles during execution; an AOT compiler pays the entire compile cost up front and ships a finished binary, so the program starts at full speed with no warm-up. Because compilation is finished before startup, the compiler can see the whole program at once — it optimizes with static facts and performs closed-world analysis, keeping only code reachable from the entry points and eliminating the rest. That is also the price: nothing can be compiled after the build, so anything the analysis did not see — dynamically loaded classes, reflection, proxies — simply is not there. Here a compiler folds a program's instructions at build time and seals the reachable ones into a NativeImage that carries no compiler at all.
GraalVM Native Image (Java / Scala) — its native-image tool compiles a JVM application and everything it can prove reachable into a single self-contained executable that starts in milliseconds with no JVM warm-up; Rust (LLVM); the Go compiler; NativeAOT (C#); Kotlin/Native; LDC2 (D). This is a runnable Maven project; see the README.md in this concept's folder in the cloned repository.

The build does three things, all before the first input exists: closed-world analysis decides what is reachable, optimization folds each surviving program, and emission seals them into the image. Programs outside the reachable set are never compiled — exactly what native-image does when it drops classes no entry point can reach:

public static NativeImage compile(List<Program> allPrograms, Set<String> entryPoints) {
  Map<String, IntUnaryOperator> compiledCode = new LinkedHashMap<>();

  for (Program program : allPrograms) {
    // Unreachable code is dead-code eliminated: it is not compiled, and there is
    // no second chance to compile it later — that is the closed-world bargain.
    if (entryPoints.contains(program.name())) {
      compiledCode.put(program.name(), emit(optimize(program)));
    }
  }

  return new NativeImage(compiledCode);
}

The optimizer uses only what is knowable statically. The accumulator's value is unknown — that is the input — but the instructions are fully known, so adjacent steps that combine algebraically collapse into one. Five instructions become two, and every run of the shipped binary gets that saving for free:

// [MUL 2, MUL 3, ADD 10, SUB 4, ADD 1]  ->  [MUL 6, ADD 7]
public static Program optimize(Program program) {
  List<Op> folded = new ArrayList<>();

  for (Op op : program.ops()) {
    // Rewrite SUB n as ADD -n so additions and subtractions can merge together.
    Op normalized = op.code() == OpCode.SUB ? new Op(OpCode.ADD, -op.operand()) : op;
    Op previous = folded.isEmpty() ? null : folded.get(folded.size() - 1);

    if (previous != null && previous.code() == OpCode.ADD && normalized.code() == OpCode.ADD) {
      folded.set(folded.size() - 1, new Op(OpCode.ADD, previous.operand() + normalized.operand()));
    } else if (previous != null && previous.code() == OpCode.MUL && normalized.code() == OpCode.MUL) {
      folded.set(folded.size() - 1, new Op(OpCode.MUL, previous.operand() * normalized.operand()));
    } else {
      folded.add(normalized);
    }
  }

  return new Program(program.name(), folded);
}

The shipped artifact holds nothing but finished code — no source, no interpreter, no compiler, no profiler. A program left out of the build cannot be compiled on demand, because there is nothing left to compile it with; a JIT would just compile it on first use, an AOT binary can only fail. This is the same failure a native-image build produces for a class reflection reaches but the analysis never saw:

public int run(String programName, int input) {
  IntUnaryOperator code = compiledCode.get(programName);

  if (code == null) {
    throw new IllegalArgumentException(
        "not in the image: " + programName + " — it was not reachable at build time");
  }

  return code.applyAsInt(input);   // straight into finished code, no warm-up
}

The tests pin the defining properties — everything is compiled before the first run, the first call is as fast as the thousandth, folding shrinks the code without changing its meaning (overflow included, since two's-complement + and * stay associative), and eliminated code stays gone:

@Test
void compiledImageMatchesReferenceSemanticsForAllInputs() {
  Program source = poly();
  NativeImage image = AotCompiler.compile(List.of(source), Set.of("poly"));
  for (int input = -100; input <= 100; input++) {
    assertEquals(Interpreter.interpret(source, input), image.run("poly", input));
  }
}

@Test
void eliminatedCodeCannotBeCompiledAtRunTime() {
  Program unreachable = new Program("unused", List.of(new Op(OpCode.ADD, 99)));
  NativeImage image = AotCompiler.compile(List.of(poly(), unreachable), Set.of("poly"));

  assertThrows(IllegalArgumentException.class, () -> image.run("unused", 1));
}

Why bother: instant startup and flat, predictable performance from the first request — no warm-up curve, no compiler competing for CPU and memory inside your process, and a much smaller artifact once unreachable code is dropped. That combination is why native-image suits short-lived and scale-to-zero workloads (CLIs, serverless functions, containers) where a JVM would still be warming up when the process exits. The trade-offs: the world is closed, so reflection, dynamic proxies and runtime class loading need explicit configuration or they vanish from the image; builds are slow and target a specific platform; and the compiler optimizes on static guesses only — it never sees the real workload, so a long-running JIT can eventually beat it on peak throughput using profile data AOT could not have.
