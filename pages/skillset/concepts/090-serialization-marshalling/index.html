Serialization / marshalling

An object lives as a graph of references in memory — a private layout the process alone can read. To store it in a file, put it in a cache, or send it over a socket, it must first become a flat sequence of bytes. Serialization (also called marshalling) is that flattening: it walks every reachable field of an object and writes a self-describing byte stream; deserialization reads the stream back and reconstructs an equal object graph. The bytes are portable — they carry no pointers, so they survive being written to disk or crossing the network to another process. Only the object's declared serial state travels: its identity is not preserved (you get a brand-new instance), and transient fields are skipped. Here a Serialization helper marshals an Account — holding a tag collection and a nested Contact — to a byte[] and back.
Jackson / ObjectOutputStream (Java); serde (Rust); json.Marshal (Go); circe / upickle (Scala); pickle (Python); protobuf (polyglot). This is a runnable Maven project; see the README.md in this concept's folder in the cloned repository.

Marshalling writes the graph to a stream; unmarshalling reads it back. Java's built-in mechanism emits a stream header — the magic bytes 0xAC 0xED — then a description of each class and its field values, recursively. The caller passes the expected type so the reconstructed object comes back already cast:

public static byte[] serialize(Serializable object) {
  ByteArrayOutputStream bytes = new ByteArrayOutputStream();
  try (ObjectOutputStream out = new ObjectOutputStream(bytes)) {
    out.writeObject(object);      // walk the graph, flatten it to bytes
  } catch (IOException e) {
    throw new UncheckedIOException("serialization failed", e);
  }
  return bytes.toByteArray();
}

public static <T> T deserialize(byte[] data, Class<T> type) {
  try (ObjectInputStream in = new ObjectInputStream(new ByteArrayInputStream(data))) {
    return type.cast(in.readObject());   // rebuild the graph from bytes
  } catch (IOException | ClassNotFoundException e) {
    throw new IllegalArgumentException("deserialization failed", e);
  }
}

An object opts in by implementing Serializable. Every non-transient field is part of the serial state and travels — including collections and nested objects, so the whole graph is captured. A field the wire must never carry (a per-session secret) is marked transient and is simply left out; it returns at its default value. The serialVersionUID stamps the format so incompatible old bytes are rejected rather than silently misread:

public final class Account implements Serializable {
  private static final long serialVersionUID = 1L;

  private final String id;
  private final long balanceCents;
  private final List<String> tags;       // a collection — part of the graph
  private final Contact contact;         // a nested object — also part of the graph
  private final transient String sessionToken;   // NOT serialized
}

The round trip is lossless for the value but not for identity: deserialize(serialize(x)) equals x, yet it is a distinct instance — a deep copy. Every nested object is a fresh instance too, because the graph was rebuilt from bytes rather than shared:

Account original = /* ... */;
Account copy = Serialization.deserialize(Serialization.serialize(original), Account.class);

original.equals(copy);              // true  — same value
original == copy;                   // false — a brand-new instance
original.contact() == copy.contact();   // false — the whole graph was rebuilt

The tests pin the defining properties — round-trip fidelity, a portable byte stream, a distinct deep copy, and that transient state is not written:

@Test
void producesPortableByteStream() {
  byte[] wire = Serialization.serialize(sampleAccount(null));
  assertTrue(wire.length > 0);
  assertEquals((byte) 0xAC, wire[0]);   // Java serialization stream magic
  assertEquals((byte) 0xED, wire[1]);
}

@Test
void transientFieldIsNotSerialized() {
  Account original = sampleAccount("secret-session-token");
  Account copy = Serialization.deserialize(Serialization.serialize(original), Account.class);
  assertNull(copy.sessionToken());     // the secret never went on the wire
}

Why bother: serialization is the boundary between a program's private memory and everything outside it — persistence, caches, message queues, and RPC all need objects turned into bytes and back. A stable, versioned format lets one process (or a later run of the same process) rebuild exactly what another produced. The trade-offs: the format is a contract — change a class carelessly and old bytes no longer deserialize; Java's native serialization in particular is verbose, JVM-only, and a notorious security risk, because readObject can be coaxed into constructing arbitrary types (deserialization of untrusted data is a classic remote-code-execution vector). Real systems therefore usually marshal to an explicit, cross-language schema — JSON, Protocol Buffers, Avro — rather than the language's built-in object stream.
