JIT compilation

Code can be interpreted — walked and executed step by step, which starts instantly and stays flexible but re-does the dispatch work on every run — or compiled ahead of time to native code, which runs fast but pays the compile cost up front for code that might never run. A just-in-time (JIT) compiler takes the middle path: it runs code interpreted at first, profiles which parts run often, and compiles only those hot paths to optimized code while the program is running. This is adaptive optimization — you pay the compile cost only for code that has proven it runs enough to earn it. The defining rule: a JIT may change speed, never behavior — the compiled code must produce exactly what interpreting would. Here a miniature Jit engine runs a small bytecode program interpreted while it is cold, then compiles it to a specialized callable once it turns hot.
JIT in HotSpot (Java / Scala / Clojure), V8 (JavaScript), the CLR (C# / F#); LuaJIT (Lua); PyPy (Python); Cranelift (Rust / Wasmtime). This is a runnable Maven project; see the README.md in this concept's folder in the cloned repository.

The engine keeps a per-program call counter — its profile. While the count is below the compile threshold, every call interprets the bytecode, dispatching one opcode at a time. On the first call past the threshold the program is compiled once, and from then on the hot program runs the compiled code. Real JITs use large counters (HotSpot's default -XX:CompileThreshold is ~10000); a small value keeps the demo fast:

public int run(Program program, int input) {
  int count = invocationCounts.merge(program.name(), 1, Integer::sum);

  // Compile exactly once, on the first call past the threshold: the program
  // has now proven itself hot, so it is worth the one-time cost of compiling.
  if (!compiledCode.containsKey(program.name()) && count > compileThreshold) {
    compiledCode.put(program.name(), compile(program));
  }

  IntUnaryOperator hotCode = compiledCode.get(program.name());
  return hotCode != null ? hotCode.applyAsInt(input) : interpret(program, input);
}

The interpreter walks the instruction list every call. The compiler folds that whole list into one callable ahead of any input, so running the compiled form no longer loops over or dispatches the bytecode — that work was done once. Both route through the same OpCode.apply, so they cannot disagree:

static int interpret(Program program, int input) {
  int accumulator = input;
  for (Op op : program.ops()) {        // walk the bytecode every call
    accumulator = op.applyTo(accumulator);
  }
  return accumulator;
}

static IntUnaryOperator compile(Program program) {
  IntUnaryOperator code = IntUnaryOperator.identity();
  for (Op op : program.ops()) {        // fold the bytecode ONCE, ahead of any input
    IntUnaryOperator preceding = code;
    code = input -> op.applyTo(preceding.applyAsInt(input));
  }
  return code;
}

A program starts interpreted; once it has run past the threshold it turns hot and switches to compiled code — with the same result either way. The switch is invisible except in speed:

Jit jit = new Jit(4);          // compile a program after 4 interpreted calls
jit.run(program, 7);           // call #1  -> interpreted, returns 27
// ... calls #2, #3, #4 ...    // still interpreted
jit.run(program, 7);           // call #5  -> now compiled, still returns 27

The tests pin the defining properties — cold code is interpreted but correct, hot code gets compiled, the compiled form is observably identical to interpreting for every input, and each program is profiled on its own (like a real JIT compiling individual hot methods):

@Test
void compiledCodeMatchesInterpreterForAllInputs() {
  Program program = poly();
  IntUnaryOperator compiled = Jit.compile(program);
  for (int input = -100; input <= 100; input++) {
    assertEquals(Jit.interpret(program, input), compiled.applyAsInt(input));
  }
}

@Test
void programsAreProfiledIndependently() {
  for (int call = 0; call < 6; call++) jit.run(hot, 7);   // this one turns hot
  jit.run(cold, 7);                                       // called once — stays cold
  assertTrue(jit.isCompiled(hot));
  assertFalse(jit.isCompiled(cold));   // making one hot does not compile the other
}

Why bother: a JIT gets both fast startup and fast steady-state — it interprets immediately, then compiles the hot loops for near-native throughput once they prove worth it, and never spends effort compiling cold code that rarely runs. Compiling during execution also lets the compiler specialize to how the code is actually being used, not just how it was written. The trade-offs: the compiler runs inside your process, competing for CPU and memory, and adds warm-up time before the fast code exists; real engines can also deoptimize — fall back to the interpreter when an assumption a compilation was built on turns out to be wrong. This project keeps a fixed threshold and no deoptimization to stay small, but the shape — interpret, profile, compile the hot path — is the essence.
