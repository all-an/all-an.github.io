Plugin / extension system

Dynamic linking loads a library you named; a plugin system loads implementations you never named. The host publishes an interface and a discovery rule, and anything on the path that satisfies both becomes part of the program at startup — new behaviour without recompiling the host, which is the open/closed principle enforced by late binding.

ServiceLoader (Java), MEF (C#), trait objects behind dlopen (Rust), compiler plugins (Scala), gems (Ruby).

The host depends only on the contract. It never mentions a concrete class, so adding a codec means adding a jar, not editing this file:

public interface Codec {           // the extension point
    String name();
    byte[] encode(String input);
}

for (Codec codec : ServiceLoader.load(Codec.class)) {   // whoever is on the classpath
    System.out.println(codec.name());
}

A provider declares itself in metadata — module-info.java, or META-INF/services/Codec on the classpath — and the runtime does the wiring:

module gzip.codec {
    requires codec.api;
    provides Codec with com.example.GzipCodec;   // discovered, never imported by the host
}

The cost: the compiler stops checking that anything is there. A missing provider is an empty iterator at runtime, not a build error; a bad one runs with the host's full permissions, in the host's process, and can hang or crash it. And the interface becomes a public API — once plugins exist, changing it breaks code you do not own. Version the extension point, isolate providers if you do not trust them, and keep the contract small enough that you can live with it.
